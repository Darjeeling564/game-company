## 7. 直したもの・作ったもの（STEP6.5-B）

### 7-1. 【音の穴】`setupDone` が 800回鳴っていなかった

400戦ぶんのログ種別を数え、`sound.ts` の `SFX` と突き合わせた。

```
attachEnergy 6067 音あり / damage 5929 音あり / beginTurn 5251 音あり
attack 4352 音あり / playCreature 4115 音あり / setupPlace 1610 音あり
item 1567 音あり / action 1548 音あり / ko 1536 音あり / promote 1130 音あり
setupDone 800 ★音なし
endTurn 545 音あり / coin 545 音あり / selfDamage 456 音あり / poison 440 音あり
start 400 ★音なし / end 400 ★音なし
gainEnergy 377 音あり / searchCreature 361 音あり / ultimate 351 音あり
switchOpponent 279 音あり / status 266 音あり
```

音が無いのは3種だった。うち `start` と `end` は**別経路で鳴っている**
（`end` は `render()` が `win` / `lose` / `draw_game` を鳴らす）。
**本当の穴は `setupDone` だけ**である。

`setupDone` は「相手が初期配置を終えた」瞬間に出る。ここが無音だと、
盤が動き出したことに気付くのが1テンポ遅れる。盤が整う音として、
`setupPlace` の木の音を2つ、間を空けて置いた。`sound.ts` の `SFX` に
足しただけで、`main.ts` は触っていない（`playFromLog` が `hasSfx` で拾う）。

**鳴っていることを実機で確かめた。**

```
SFX 表の確認: {"ok":true,"has":true,"hasPromote":true}
準備完了を押した前後の音源: オシレータ 26 → 30 / ノイズ源 4 → 5
```

上段は、動いているページから `sound.ts` を読み込んで `hasSfx('setupDone')` を
呼んだ結果である（ソースを読んだのではなく、**実行時の表**を見ている）。
下段は `AudioContext.prototype.createOscillator` と `createBufferSource` を
数えたもの。`setupDone` は「ノイズ1＋オシレータ2」なので、**ノイズ源の +1 は
この音のぶん**であり、オシレータの +4 には同時に鳴る `beginTurn` などが含まれる。

### 7-2. 【新しい演出】エネルギーを剥がされた瞬間（SPEC 9.4.9）

#### なぜ必要か — `discardEnergy` はログに1行も出ない

上のログ種別の表に **`discardEnergy` が無い。** 400戦回して0回である。
`core/effects.ts` の該当節は状態だけを書き換えて `log()` を通さない。
damage も poison も switchOpponent も searchCreature も status も
ログに出るのに、**この効果だけが黙っている。**

ログに出ない ⇒ 音も鳴らない（9.6 はログ種別で鳴らす）⇒ 演出も無い。
プレイヤーに残る手がかりは**相手のカードのエネルギーの丸が1つ減ること**だけだった。

珍しい効果ではない。**姫神のワザ18件**と支援カードが持っている。

#### 直しかた

SPEC 9.4.9 を先に追記してから実装した。毒（9.4.7）と同じ差分方式である。

`prevEnergy` は既に「増えたら `.card--charged`」の判定に使っている。
**同じ値の減少側を見るだけ**で済み、**core には触っていない。**

```ts
if (energy !== undefined && c.attached.length > energy) charged.add(c.instanceId)
if (energy !== undefined && c.attached.length < energy) drained.add(c.instanceId)
```

**カード本体の `transform` は動かしていない。** エネルギーを剥がすワザは
同時にダメージも与えるので `.card--hit` と同じカードに乗る（毒で踏んだのと同じ理由）。
`prefers-reduced-motion: reduce` の一覧にも `.card--drained` を足した。

#### 色を1度やり直した

最初は増える側の金と対にして `rgba(112, 122, 112)` の**緑がかった灰**にしたが、
実機の写真で **halo がほとんど読めなかった**。盤の森緑と明度も色相も近いためである。

| | 色 | 止めた時点の実測 | 読めたか |
|---|---|---|---|
| 1回目 | rgba(112, 122, 112) | `0.776 / blur 11.9px / spread 4.6px` | **ほとんど読めない** |
| 2回目 | **rgba(198, 210, 218)**（冷たい鋼色） | `0.843 / blur 13.7px / spread 5.5px` | **読める** |

緑の盤からも、金の `--charged` からも離れる色にした。

#### 対戦中に出ることを確かめた

```
■ エネルギーを剥がされた演出が対戦中に出た（1試合目 / 175手目）
  [{"名前":"フェンリル","側":"相手","anim":"cardDrain",
    "同時に乗ったクラス":"card--board card--active card--drained",
    "止めた時点の影":"rgba(198, 210, 218, 0.843) 0px 0px 13.7164px 5.48655"}]
```

スクリーンショット: [`shots-2026-09-16/fx-drained.png`](shots-2026-09-16/fx-drained.png)

**撮り逃しを1度している。** 1回目は数えられたのに写真に残らなかった。
`root.replaceChildren()` の次の描き直しが 150ms 以内に来て、**要素ごと消える**ためである。
描き直しは CPU の手番タイマー（`window.setTimeout`）から来るので、
確認用のページ側でそのタイマーを止めてから撮るようにして解決した。
**game 側のコードは変えていない。**

### 7-3. 【計測ツールの誤り】半透明の背景を重ね合わせていなかった

今夜の1回目の計測は **低コントラスト 124件**を出した。中身を見ると
`.gallery__rarity`（1.35:1）や `.meter__hp`（1.57:1）で、**どちらも実際には読める。**

原因は背景色の求め方だった。「不透明な祖先が出るまで遡る」という作りで、
`.gallery__rarity` の `rgba(14, 30, 19, 0.85)` のような**濃い半透明の下敷きを
素通りして**、ページ地のクリームと比べていた。クリーム文字 対 クリーム地で 1.35:1 になる。

**半透明を順に重ね合わせて求める**ように直したところ、**124件 → 0件**になった。
これは 2026-09-04 に一度踏んだ誤報告と同じ筋のもので、
計測スクリプトを書き直すたびに再発しうる。
