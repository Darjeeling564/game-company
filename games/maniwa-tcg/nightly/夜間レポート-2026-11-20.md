## 4. 姫神演義（B の夜）— 連打しているあいだ相手が動けない

### 4.1 なぜここを測ったか

**姫神戦記で 11-19 に見つけた欠陥の裏返しを探した。** あちらは `render()` が
ドローの待ちを**無管理で積み増していた**。姫神演義の `render()` は逆に
**先頭で `clearTimer()` を呼んでいる**ので積まない。
**ならば「消しすぎ」のほうが起きていないか**を測った。

### 4.2 仕組み

```ts
function render(): void {
  clearTimer()          // ← 相手の待ちを毎回消す
  …
  if (cpuShouldMove()) {
    cpuTimer = window.setTimeout(…, CPU_DELAY_MS)   // ← 450ms で作り直す
  }
}
```

`openOverlay()` と `closeOverlay()` はどちらも `render()` を呼ぶ。
**カードを1枚つつくだけで `render()` が走る。** 盤は何も動かないのに、
**相手の待ちは毎回ゼロから数え直される。**

### 4.3 ★ ここで計測を1回まちがえた

`window.setTimeout` をページ側で包み `ms === 450` を数えたが、
**450ms のタイマーは2種類あった。**

| 定数 | 置き場 | 用途 |
|---|---|---|
| `CPU_DELAY_MS = 450` | `main.ts:38` | 相手の待ち |
| `LONG_PRESS_MS = 450` | `view.ts:396` | 長押しの判定 |

`bindTap` は `pointerdown` で長押しのタイマーを作り `pointerup` で消すので、
**タップ1回ごとに「作成→1ms で取消」が1組出る。** これを一緒に数えて、
**最初は「595本作って594本取消」という10倍以上に盛った数字を出した。**
呼び出し元のスタックを見て気付き、**`main.ts` の `render` から出たものだけに絞って
測り直した。**

> **★ 値で絞り込むときは、同じ値を使う別のものが無いかを必ず見る。**
> 「同じ値を2か所に別々に書かない」とは言ってきたが、
> **この2つは無関係なので統一すべきではない。** 揃えるべきでない同値が、
> **計測の側で取り違えを生む**という形である。

### 4.4 実測 — 基点の木と並べた

手札をつつく→開いた画面を閉じる、を一定の間隔で繰り返して30秒。
**盤は動かさず、詳細を読むだけ**である。

| タップの間隔 | タップ数 | 作った | 取り消した | **相手が動いた回数** | |
|---|---|---|---|---|---|
| **触らない** | 0 | 1 | 0 | **2** | — |
| 600ms | 79 | 4 | 3 | 2 | |
| 250ms | 148 | 148 | **148** | **0** | **★** |
| 150ms | 208 | 208 | **208** | **0** | **★** |
| 100ms | 242 | 243 | **242** | **1** | |

**250ms と 150ms では、30秒のあいだ相手が1手も動かない。**
取り消しまでに待った最長は 320〜424ms で、**どれも 450ms に届いていない。**

> **★ 1回の繰り返しで `render()` は2回走る**（つつく＋閉じる）。
> 「間隔 250ms」でも実際の描き直しは 125ms おきである。
> **間隔の数字をそのまま「人の連打の速さ」と読まないこと。**

### 4.5 直したもの

- **`clearTimer()` を無条件で呼ぶのをやめた。** `cpuShouldMove()` が偽のときだけ消す
- **待ちが既にあるなら作り直さない**（`cpuTimer === null` のときだけ作る）
- **発火したら `cpuTimer` を null に戻す。** 条件付きにしたので自分で後始末する
- **`core` も `CPU_DELAY_MS` も触っていない。既存の演出も1つも触っていない**

### 4.6 直したあとの実測（同じ物差し）

| タップの間隔 | タップ数 | 作った | 取り消した | **相手が動いた回数** |
|---|---|---|---|---|
| 触らない | 0 | 1 | **0** | **2** |
| 600ms | 82 | 3 | **0** | **4** |
| 250ms | 150 | 2 | **0** | **3** |
| 150ms | 194 | 1 | **0** | **2** |
| 100ms | 246 | 2 | **0** | **3** |

**取り消しが全ペースで0。** 相手が動く回数は**触らないときと同じかそれ以上**になり、
連打の速さに依らなくなった。

### 5.3 仕組みと直し方

`.board` は縮むが**中の `.board__table` は縮まない**。`.board` が内容より低くなると
`justify-content: center` のまま**上下に均等にはみ出し**、下側が手札に被る。
`.board` に溢れの扱いが無いので、**はみ出した絵がそのまま手札の上に描かれる。**

**姫神演義の `.field` と同じ「盤の中で送る」形にした**（姫神演義 SPEC 9.3.1）。

- `overflow-y: auto` を足す。**高さの値は1つも変えていない**
- `center` → `safe center`。`overflow` を付けた中央寄せは、
  入りきらないとき**上側がはみ出して掴めなくなる**

**代わりに、低い画面では一度に見える枠が減る**（12 → 9 → 6 → 3）。
**盤の中で送れば全部に届く**ので、重なって触れなくなるより良い。

### 5.4 ★★ ここで計測器を2回まちがえた。どちらも「直した後だけ」壊れる形だった

1. **最初は枠と手札の矩形をそのまま交差させた。** 直したあとは `.board` が中身を
   **切り取る**ので、切り取られて描かれていない枠まで「重なっている」と数え、
   **直したのに悪化した（0→3、3→6）という嘘の結果**が出た
2. **そこで盤の矩形で切り取るようにしたら、今度は「直す前」が全部0になった。**
   `overflow: visible` のときは**盤の外もそのまま描かれる**ので切り取ってはいけない

正しい形は「**`overflow` を見てから当てる**」。`visible` なら素の矩形、
それ以外なら盤で切り取った矩形を使う。
**2026-10-02 に文字の切れで学んだのと同じ形だが、あのときは `hidden` を前提にして
`visible` に当ててしまい、今回は逆に `visible` を切り取った。**
向きが逆でも原因は1つで、**「描かれているか」は要素の矩形だけでは決まらない。**
