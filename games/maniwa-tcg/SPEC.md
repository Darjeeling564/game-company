# maniwa-tcg 仕様書

**美少女バトルのカードゲーム**。世界の神話の神格を美少女として擬人化し、2人で戦わせる。
ルール骨格はポケモンカードゲームポケット（デッキ20枚 / バトル場1体＋ベンチ3体 /
エネルギー自動供給 / ポイント先取）を題材とする。

画面上のタイトルは **「姫神演義」**。`maniwa-tcg` はディレクトリとセーブキー
（`maniwa-tcg_v1`）に使う内部の識別子で、表示名とは切り離してある。表示名を変えるときは
`index.html` の `<title>` と `main.ts` のタイトル画面の2箇所だけを直せばよい。

本書は実装の基準となるドキュメントである。14章の論点は**すべて決定済み**であり、実装に着手してよい。

---

## 1. v1 スコープ

CLAUDE.md 7章「バーティカルスライス優先」に従い、v1 は**対戦ループ1本を完成品質で通す**ことを目標とする。

### v1 に含む

- 2人対戦（プレイヤー vs CPU、および CPU vs CPU のシミュレーション）
- たね（進化なし）クリーチャーのみ
- バトル場 / ベンチの管理、にげる
- エネルギーの自動供給と付与
- 攻撃、弱点、きぜつ、ポイント獲得、勝敗判定
- 効果タイプ: ダメージ / コイン依存ダメージ / 回復 / 自傷 / エネルギートラッシュ / ベンチへのダメージ / どく
- 決定論リプレイ（シード + 入力列 → 状態ハッシュ一致）

### v1 に含まない（v2 以降）

- 進化、特性
- アイテム / 行動 / 絶技のカード（**16章に設計案。承認後に着手する**）
- ねむり / まひ / こんらん（ターン境界でのコイン処理が必要なため）
- オンライン対戦、デッキ編集 UI、カードの量産

**カードデータのスキーマは v2 の要素も表現できる形で先に確定させる**（8章・14章参照）。スキーマを後から壊さないことを優先する。

## 2. 用語

| 用語 | 意味 |
|---|---|
| クリーチャー | 場に出して戦うカード。ポケモンに相当 |
| バトル場 | 攻撃・攻撃対象になる位置。常に0体または1体 |
| ベンチ | 控え。最大3体 |
| EX級 | きぜつ時に相手へ2ポイント与える強力なクリーチャー |
| 個体 | 場に出たクリーチャー1体分の状態。同じカードでも別個体 |
| エネルギー | 攻撃コストとして個体に付与する資源。カードとしては存在しない |
| ポイント | 相手をきぜつさせて得る点数。3点先取で勝利 |

## 3. ルール

### 3.1 デッキ構築

- 20枚ちょうど
- 同名カードは2枚まで（`CardDef.name` で判定する。`id` ではない）
- クリーチャーを最低1枚含む（v1 は全カードがクリーチャーなので自明）
- デッキごとに**エネルギータイプを1〜3種**指定する。これが供給されるエネルギーの抽選元になる

#### 3.1.1 基準デッキとプールデッキ

デッキの作り方は**2通り持つ**。目的が違うので、片方に寄せてはいけない。

| モード | 内訳 | 何に使うか |
|---|---|---|
| **基準デッキ**（`fixed`） | 固定の20枚。属性ごとに1つ、計8デッキ | バランス指標の基準線。12章の数値はこちらで測る |
| **プールデッキ**（`pool`） | カードプール全体から20枚を抽選する | プールに増えたカードの性能確認 |

**基準デッキはカードを足しても変えない。** 12章の指標（先手勝率・平均ターン数・
デッキ別平均勝率のレンジ）は、デッキが固定であってはじめて日をまたいで比較できる。
デッキが自動で変わると、数値が動いた理由がカードのせいか構成のせいか切り分けられない。

そのため `decks.ts` の `MAIN_PER_DECK = 8` で専用キャラ枠を8枚に固定している。
属性に9体目を足しても基準デッキは20枚のまま、9体目は基準デッキに入らない。

**プールデッキは新しいカードを測るためにある。** 基準デッキだけだと、あとから
足したカードは永久に一度も戦わず、採用率も勝率寄与も出せない（12章が前提を失う）。

##### プールデッキの抽選ルール

内訳は基準デッキと同じ（専用キャラ8 / 無4 / 神具3 / 道標3 / 絶技1種×2枚）。
そのうえで次を守る。

1. **シード付き抽選にする。** 決定論を壊さないため、`Math.random` は使わず
   `core/rng.ts` の PRNG をシードから回す（3章の制約と同じ理由）
2. **強い順に選ばない。** 強さで選ぶと、弱いカードは選ばれず、選ばれないから
   測れず、測れないから弱いと分からない循環に入る。**死に札の検出ができなくなる**
   （u003 黄の印 は実際にこの検出で見つかった）。一様抽選にして、試行回数で均す
3. **絶技は対応キャラを必ず同居させる。** 対応キャラがいない絶技は死に札で、
   デッキ検証（`validateDeck`）でも弾かれる
4. 同名2枚までの制限は基準デッキと同じ

1万戦回せばプール内の全カードが十分な回数使われるので、**カードを足した翌日から
何もしなくても性能が測られる**状態になる。

### 3.2 ゲーム開始

1. シードから PRNG を初期化する
2. 先攻を決める（`start` アクションで外部から与える。シミュレーションでは交互 / ランダムを選べる）
3. 両者デッキをシャッフルし、**先攻は5枚・後攻は6枚**引く
   （後攻の1枚は先手対策。レアリティ召喚を入れると先手勝率が 54.33% になるため。3.3.1 参照）
4. 手札にクリーチャーが1枚も無ければ、手札をデッキに戻して引き直す（最大10回。10回失敗したらそのデッキは不正としてエラー終了）
5. 両者がバトル場に1体、任意でベンチに最大3体を伏せて出す（`setupPlace` / `setupDone`）
6. 先攻のターン1へ

### 3.3 ターン進行

ターン開始時に自動で以下を行う（プレイヤーの操作は不要）:

1. **エネルギー供給** — デッキのエネルギータイプから1つ抽選し、エネルギーゾーンに置く
2. **ドロー** — 1枚引く。デッキが空なら引かない（**山札切れによる敗北は無い**）
3. にげる使用フラグ / エネルギー付与フラグをリセット

メインフェーズでは以下を任意の順・任意の回数（制限があるものは記載どおり）行える:

| 行動 | 制限 |
|---|---|
| ベンチにクリーチャーを出す | ベンチが3体未満のとき。回数制限なし |
| エネルギーを付与する | **1ターンに1回**。エネルギーゾーンに在庫があるとき |
| にげる | **1ターンに1回**。バトル場の個体からにげるコスト分のエネルギーをトラッシュし、ベンチの1体と入れ替える |
| 攻撃する | **1ターンに1回。攻撃するとターンが終了する** |
| ターンを終了する | いつでも |

ターン終了時に **どく** の処理を行う（3.4 参照）。

#### 先攻1ターン目の制限

- **攻撃できない**
- **エネルギーは供給される**（禁止されるのは攻撃のみ。14章 Q1 で決定済み）

### 3.3.1 レアリティ召喚（姫神を出すときの制限）

> **状態: 承認済み・実装済み**（2026-08-28）。
> 試作の経緯は実験ブランチ `experiment/rarity-summon` に残してある（マージしない）。

姫神を場に出すとき、**レアリティに応じて場の姫神を1体リリースする**。

| レアリティ | 出すのに必要なもの |
|---|---|
| C（コモン） | なし。空きベンチにそのまま出せる |
| R（レア） | エネルギーが**1つ以上**付いた場の姫神を1体リリース |
| SR（スーパーレア） | エネルギーが**2つ以上**付いた場の姫神を1体リリース |
| UR（ウルトラレア） | エネルギーが**3つ以上**付いた場の姫神を1体リリース |

- **エネルギーの種類は問わない。** 個数だけを見る
- リリースした姫神が**バトル場にいたらバトル場に**、**ベンチにいたらその枠に**出す
- リリースされた姫神はトラッシュへ送る。**ポイントは動かない**（きぜつではない）

#### リリース元のエネルギーは引き継ぐ

**出した姫神は、リリース元に付いていたエネルギーをそのまま持って登場する。**
ダメージは引き継がず、0から始まる。

これが無いと「3ターン貯める → 捨てる → また3ターン貯め直す」で1体に6ターン以上かかり、
**絶技が撃てなくなる**。絶技10種のうち9種は対応姫神が UR EX なので、
引き継ぎが無い設計は絶技を全滅させる。

引き継ぎを入れると逆に**現行より速くなる**。3エネ貯めた姫神をリリースして UR EX を出すと、
その UR EX は3エネを持って登場するため、その場で絶技を撃てる。
現行は「EX を置いてから3ターン待つ」なので、2〜3ターン短縮される。

#### 配置フェーズ（ゲーム開始時）はレアリティ制限を適用しない

**ゲーム開始時の配置だけは、レアリティに関係なく置ける。**

配置フェーズには場に姫神がいないのでリリース元が存在せず、制限を適用すると
**初手にコモンの姫神が無いプレイヤーは何も置けずに詰む**。

実測（8デッキ × 5000回）:

| | 確率 |
|---|---|
| 初手5枚に姫神が1体もいない（現行でも起きる） | 0.4% |
| 初手5枚に**コモンの姫神**がいない | **10.6%** |

両プレイヤーのどちらかが該当する確率は約20%。実際に制限を掛けて1万戦回すと
**引き分けが 18.9%** になり、`tests/termination.test.ts` の終局保証が3件落ちた。
配置フェーズを自由にすると引き分けは 0.0% に戻る。

#### 先手対策 — 2つ同時に入れる

このルールだけを入れると**先手勝率が 54.33% に上がる**。先手が先にエネルギーを
貯めてリリースできるぶん有利になるため。次の2つを併用して 49.8% に戻している。

1. **後手は初期手札を1枚多く引く**（5枚→6枚。3.2 の変更）
2. **先攻1ターン目はリリースできない**（コモンをそのまま出すのは可）

##### 検証: 単独では成立しない

4シード × 3万戦で全パターンを測った。**2つとも入れないと基準を満たさない。**

| 構成 | 先手勝率 | 判定 |
|---|---|---|
| 対策なし | 54.33% | 基準内だが上限寄り |
| **2 のみ**（先攻1ターン目のリリース禁止） | **55.30%** | ❌ **基準（55%）超過** |
| 1 のみ（後手の初期手札 +1） | 48.77% | OK |
| **1 + 2（採用）** | **49.80%** | ✅ 最も 50% に近い |

**2 は単独だと逆効果になる。** 設計時は「先手の初動を止める」つもりだったが、
実測では**先手を 1pt 有利にする**方向に働いた（54.33→55.30 / 48.77→49.80 と、
どちらの比較でも一貫して +1pt）。おそらく貪欲AIが先攻1ターン目に
割の悪いリリースをしており、それを禁じると結果的に先手が得をしている。

1 だけでも基準は満たす（48.77%）が、2 を足すと 49.80% とより 50% に近づく。
2 には既存の「先攻1ターン目は攻撃できない」（3.3）と形が揃う利点もあるので、
両方を採用した。**ただし 2 の効果は当初の意図と逆であることを、ここに記録しておく。**

#### 実測（実装後・1万戦 / 10万戦）

| 指標 | 現行（変更前） | この案 | 判定 |
|---|---|---|---|
| 先手勝率（1万戦 / 10万戦） | 51.6% / 51.8% | **49.6% / 49.8%** | OK（45〜55%） |
| 引き分け率 | 0.0% | 0.0% | OK |
| 平均ターン数 | 14.7 | 13.6 | 決着が約1ターン速い |
| ポイント決着 | 98.2% | 98.7% | わずかに上昇 |
| ターン上限到達 | 0.0% | 0.0% | OK |
| pool の未使用カード | 0件 | 0件 | OK |
| テスト | 139件合格 | 139件合格 | OK |

**狙いどおりレアリティが機能する。** 勝率寄与の格差が約2倍に開いた。

| レアリティ | 現行（変更前） | この案 |
|---|---|---|
| UR | +10.3pt | **+18.7pt** |
| SR | +3.1pt | **+6.3pt** |
| R | -0.2pt | **+2.4pt** |
| C | -3.2pt | -2.2pt |

絶技の使用率も上がる（u003 黄の印 30.6%→48.0% / u001 天叢焼 35.6%→54.7%）。
リリース元の3エネを引き継いだ UR EX がその場で絶技を撃てるため。

#### 実装時に触る範囲

| 対象 | 変更 |
|---|---|
| `core/actions.ts` | `playCreature` に `release: InstanceId \| null` を追加 |
| `core/reduce.ts` | `RELEASE_COST` と、エネルギーを引き継ぐ配置処理を追加。`legalActions` は手札とリリース候補の組で列挙する |
| `tools/ai.ts` | HP が増えるときだけリリースする判断を追加（無いと育てた姫神を捨てて弱いものを出す） |
| `game/main.ts` | 手札の選択肢にリリース対象を出す。1枚につきリリース候補の数だけ選択肢が並ぶので、名前・残りHP・エネルギー数を見出しに入れる |

**注意**: リリースしたエネルギーをトラッシュに入れてはならない。エネルギーはカードではなく
別ゾーンなので、`tests/invariants.test.ts` の「カード総数20枚」が壊れる（実験で踏んだ）。

**バランスの基準値はすべて測り直しになる。** 先手勝率・平均ターン数・デッキ地力レンジ・
カード別の勝率寄与は、この変更後の数字に置き換える。

### 3.4 攻撃とダメージ

1. 攻撃には `cost`（必要エネルギーの並び）を満たす必要がある。`colorless` は任意のタイプ1個で支払える
2. `effects` を配列の先頭から順に解決する
3. ダメージ計算:
   - 基礎ダメージ = 効果の `value`（コイン依存の場合は表の数で決まる）
   - 対象がバトル場の個体で、対象の `weakness` が攻撃側個体のタイプと一致する場合、**+20**
   - ベンチへのダメージには弱点を適用しない
   - 結果が負なら0にクランプする
4. 個体に蓄積ダメージ（`damage`）として加算する

**どく**: 付与された個体は、**そのターンの終了時ごと**に10ダメージを受ける。バトル場から離れる（にげる / きぜつ）と解除される。

### 3.5 きぜつとポイント

1. すべての効果の解決後、両プレイヤーの全個体について `damage >= hp` を判定する
2. きぜつした個体は、付与エネルギーごとトラッシュへ送る
3. きぜつさせた側が **EX級なら2、それ以外は1** ポイントを得る
4. バトル場が空になったプレイヤーは、ベンチから1体をバトル場に出す（`promote`）
   - 両者が同時に空になった場合、**手番プレイヤーの相手 → 手番プレイヤー** の順に処理する
   - ベンチにも1体もいない場合は敗北条件を満たす（3.6）
5. `promote` が完了するまで他の行動は受け付けない

### 3.6 勝敗判定

以下を上から順に評価する。

| 順 | 条件 | 結果 |
|---|---|---|
| 1 | 両者が同時に3ポイント以上に達した | **手番プレイヤーの勝ち**（`endReason: 'simultaneous'`。14章 Q2 で決定済み） |
| 2 | 片方が3ポイント以上に達した | そのプレイヤーの勝ち（`'points'`） |
| 3 | バトル場が空で、ベンチにも個体がいない | そのプレイヤーの負け（`'noCreature'`） |
| 4 | ターン数が `MAX_TURNS` に達した | ポイントが多い方の勝ち。同点なら引き分け（`'turnLimit'`） |

- `MAX_TURNS = 100`（両者合計のターン数）。**終局保証テストのための上限であり、通常の対戦で到達してはならない**。到達率はシミュレーションで監視する（12章）
- 山札切れでは敗北しない

## 4. 状態の型定義

`src/core/types.ts` に置く。すべて `readonly`。core は純粋関数のみで構成する（CLAUDE.md 3章）。

```ts
export type PlayerId = 0 | 1
export type CardId = string        // 例: "c001"
export type InstanceId = number    // 場に出た個体の一意ID。単調増加

export type EnergyType =
  | 'grass' | 'fire' | 'water' | 'lightning'
  | 'psychic' | 'fighting' | 'darkness' | 'metal'
  | 'colorless'                    // コスト表記専用。供給・付与はされない

export type Status = 'poisoned'    // v1 は どく のみ

/** シード付きPRNG。状態として持ち回る（CLAUDE.md 3章） */
export interface Rng {
  readonly seed: number            // xorshift32 の内部状態
}

/** 場に出ている1体分の状態 */
export interface Creature {
  readonly instanceId: InstanceId
  readonly cardId: CardId
  readonly damage: number          // 蓄積ダメージ。hp 以上できぜつ
  readonly attached: readonly EnergyType[]
  readonly status: readonly Status[]
  readonly placedTurn: number      // 場に出たターン。v2 の進化制限で使う
}

/** エネルギーゾーン */
export interface EnergyZone {
  readonly pool: readonly EnergyType[]   // デッキが供給しうるタイプ（1〜3種）
  readonly current: EnergyType | null    // 今ターン付与できる在庫。付与すると null
  readonly next: EnergyType | null       // 次ターンに来るタイプ（UI表示用。先に抽選済み）
}

export interface PlayerState {
  readonly deck: readonly CardId[]       // 先頭が山札の一番上
  readonly hand: readonly CardId[]
  readonly discard: readonly CardId[]
  readonly active: Creature | null
  readonly bench: readonly Creature[]    // 最大3
  readonly points: number
  readonly energy: EnergyZone
  readonly attachedThisTurn: boolean
  readonly retreatedThisTurn: boolean
}

export type Phase =
  | { readonly kind: 'setup' }                                   // 初期配置待ち
  | { readonly kind: 'main' }                                    // 通常のターン
  | { readonly kind: 'promote'; readonly queue: readonly PlayerId[] }  // きぜつ後の入れ替え待ち
  | { readonly kind: 'ended' }

export type EndReason = 'points' | 'noCreature' | 'turnLimit' | 'simultaneous'

export interface LogEntry {
  readonly turn: number
  readonly player: PlayerId
  readonly kind: string            // 'attack' | 'ko' | 'rejected' | ...
  readonly detail: string
}

export interface GameState {
  readonly rng: Rng
  readonly turn: number                  // 1始まり。手番が移るたびに +1
  readonly current: PlayerId             // 手番プレイヤー
  readonly firstPlayer: PlayerId
  readonly phase: Phase
  readonly players: readonly [PlayerState, PlayerState]
  readonly setupDone: readonly [boolean, boolean]
  readonly nextInstanceId: InstanceId
  readonly winner: PlayerId | null       // null かつ phase.kind==='ended' なら引き分け
  readonly endReason: EndReason | null
  readonly log: readonly LogEntry[]
}
```

### 設計上の約束

- `CardDef`（カードの静的定義）は **`GameState` に含めない**。`cardId` で `data/cards.ts` を参照する。状態を小さく保ち、ハッシュ計算を安定させるため
- `log` は**状態ハッシュの計算対象外**。デバッグ用であり、リプレイ一致判定に影響させない
- `reduce` は**例外を投げない**。不正な Action は状態を変更せず `log` に `kind: 'rejected'` を積むだけとする。これによりシミュレーションとファジングが安全に回る

## 5. Action 一覧

`src/core/actions.ts` に置く。core の唯一の入口は `reduce(state, action)`（CLAUDE.md 3章）。

```ts
export type Action =
  // --- 開始 ---
  | { readonly type: 'start'
      readonly seed: number
      readonly decks: readonly [Deck, Deck]
      readonly firstPlayer: PlayerId }

  // --- 初期配置 ---
  | { readonly type: 'setupPlace'; readonly player: PlayerId; readonly handIndex: number }
  | { readonly type: 'setupDone';  readonly player: PlayerId }

  // --- メイン ---
  | { readonly type: 'playCreature'; readonly player: PlayerId; readonly handIndex: number }
  | { readonly type: 'attachEnergy'; readonly player: PlayerId; readonly target: InstanceId }
  | { readonly type: 'retreat';      readonly player: PlayerId; readonly benchIndex: number }
  | { readonly type: 'attack';       readonly player: PlayerId; readonly attackIndex: number }
  | { readonly type: 'endTurn';      readonly player: PlayerId }

  // --- きぜつ後 ---
  | { readonly type: 'promote';      readonly player: PlayerId; readonly benchIndex: number }
```

すべての Action が `player` を持つ。core は手番と `phase` を照合し、不一致なら拒否する。
これによりリプレイログが単体で読めるようになり、「誰の入力か」を外部状態に依存せず検証できる。

### 補助関数（core、純粋）

```ts
export function reduce(state: GameState, action: Action): GameState
export function legalActions(state: GameState): readonly Action[]   // AI・シミュレータ・UIの活性判定が共用する
export function hashState(state: GameState): string                 // log を除いた正規化 → FNV-1a
export function isOver(state: GameState): boolean
```

`legalActions` を単一の真実にすることで、「UI では押せるのに core が弾く」という不整合を防ぐ。

  readonly name: string

  | 'japan' | 'egypt' | 'norse' | 'india'

  readonly weakness: EnergyType | null       // 一致で +20

## 7. 効果（Effect）の一覧

解釈は `src/core/effects.ts` に一元化する（CLAUDE.md 4章）。

```ts
export type Target =
  | 'opponentActive'      // 相手のバトル場
  | 'opponentBenchAll'    // 相手のベンチ全体
  | 'opponentBenchRandom' // 相手のベンチから1体（PRNG使用）
  | 'self'                // 攻撃している自分の個体
  | 'ownActive'           // 自分のバトル場（self と同義だが意図を明示）

export type Effect =
  /** 対象にダメージ。弱点はバトル場への攻撃時のみ適用 */
  | { readonly type: 'damage'; readonly target: Target; readonly value: number }

  /** コインを count 回投げ、表の数 × value のダメージ */
  | { readonly type: 'damagePerHeads'; readonly target: Target
      readonly count: number; readonly value: number }

  /** コインを count 回投げ、表が min 枚以上なら then を解決 */
  | { readonly type: 'coinFlip'; readonly count: number
      readonly min: number; readonly then: readonly Effect[] }

  /** 対象の蓄積ダメージを value 回復（0未満にはならない） */
  | { readonly type: 'heal'; readonly target: Target; readonly value: number }

  /** 自分の個体に value ダメージ（反動） */
  | { readonly type: 'selfDamage'; readonly value: number }

  /** 対象から value 個のエネルギーをトラッシュ */
  | { readonly type: 'discardEnergy'; readonly target: Target; readonly value: number }

  /** 対象に状態異常を付与 */
  | { readonly type: 'applyStatus'; readonly target: Target; readonly status: Status }

  /** value 枚引く */
  | { readonly type: 'draw'; readonly value: number }
```

- `coinFlip.then` に `Effect[]` を入れ子にできる。「表なら追加40ダメージ」のような表現をデータのまま書ける
- 乱数を使うのは `damagePerHeads` / `coinFlip` / `opponentBenchRandom` のみ。いずれも `state.rng` を消費し、新しい `rng` を返す
- 効果タイプを追加するときは `effects.ts` の解釈テーブルに1件足す。それ以外のコードは触らない

### 8.1 カードプールとデッキ構成

3.1 のデッキ構築ルール（**20枚ちょうど / 同名2枚まで**）から、1デッキには最低10種が必要になる。

v1 のプールは **40種**。8系統の神話から**各5枚ずつ**均等に配分する。

| 区分 | 種類数 | 用途 |
|---|---|---|
| 無色（眷属） | 4 | 全デッキ共通のコア |
| 炎（火・太陽・破壊） | 12 | 「ほのお」デッキ |
| 草（大地・豊穣） | 12 | 「くさ」デッキ |
| 水（海・河） | 12 | 「みず」デッキ |

プリセットデッキは3つ。いずれも `専用12種 × 1枚 + 共通の無色4種 × 2枚 = 20枚`。
**プール中のすべてのカードがいずれかのデッキで使われる**構成にしてあり、
「一度も使われなかったカード」（12章）が構成上の取りこぼしで出ないようにしている。

EX 級は各タイプに1枚ずつ（カグツチEX / ユグドラシルEX / クトゥルフEX）。

系統は `origin` として項目に持つ。8.1 の表は要約であり、**データ側が真**である。
`'original'` は神話に由来しない独自キャラクター用の枠で、**v1 では未使用**。独自キャラクターを
足すときは、8系統の均等配分とは別枠として数える。

各カードは `flavor` にモチーフの解説を持つ。**必須項目**とし、書き忘れを型で防ぐ。
戦闘には影響しない表示専用のデータで、カード詳細の最下部に出す。

### 8.2 弱点と回復の制約

> **この節の弱点表は17章で置き換わった。**
> 属性は3種（草・炎・水）＋無色から**9種**（炎・水・森・土・風・雷・光・闇・無）に
> 拡張済みで、相性は `core/types.ts` の `WEAKNESS_CHART` が唯一の正とする。
> 下の3すくみの記述は**当時の設計の記録**として残してあり、実装とは一致しない。
> 現行の相性は **17.1〜17.2** を見ること。
>
> ただしこの節のうち **「回復量 < ダメージ量」の制約**（後述）と
> **「先手勝率はミラーマッチで測る」** は今も有効で、12章が参照している。
> 節ごと消さないこと。

#### （記録）当初の3すくみ

弱点は **草 → 炎 → 水 → 草** の一方向の循環とする。

| タイプ | 弱点 |
|---|---|
| 草 | 炎 |
| 炎 | 水 |
| 水 | 草 |
| 無色 | **なし**（3すくみの外側） |

無色は全デッキ共通のコアなので、弱点を持たせるとどのデッキでも同じだけ不利になり、
相性の設計に寄与しない。存在しないタイプを弱点に書くとデータが嘘をつくため、
`weakness: null` として「弱点を持たない」ことを明示する。

各デッキは1つに強く1つに弱いため、**組み合わせの勝率は大きく偏るが、全体では均衡する**。
これは設計どおりで、是正の対象ではない。ミラーマッチの勝率が50%近辺にあり、かつ
どのデッキも「有利1・不利1」を持つことが健全性の条件になる。

なお `CardDef.weakness` は17章の実装で廃止した。弱点はカードごとに書かず、
`WEAKNESS_CHART` から引く（カードを足すたびに相性表を書き写す必要がなくなる）。

なお12章の**先手勝率（45〜55%）は同一デッキどうしのミラーマッチで測定する**。
デッキ相性が混ざると手番の有利さが読めなくなるため。

#### 回復効果の制約

**ワザに回復を付けるときは、回復量をそのワザ自身のダメージ量より小さくすること。**
同値以上にすると、ミラーマッチで互いに削れない膠着が生まれ、ターン上限まで試合が
終わらなくなる（実際に到達率2.1%の退行を出したことがある）。

回復専用のアイテム・行動には、この形の制約は当てはめられない（ダメージを持たないので
比較対象が無い）。狙いは「互いに削れない膠着を作らない」ことなので、**ターン上限到達率が
0% であることをもって健全とみなす**（12章の指標で監視する）。1枚あたりの回復量ではなく、
試合を通じて回復が打点を上回らないかを見る。

### 8.3 レアリティ

レアリティは**強さと稀少性**から決める。感覚で振らず、次の手順で算出する。

1. カードごとに総合力を出す — `HP + 効率 × 3 + 最大威力 × 0.6`
   - 効率 = ワザの期待値 ÷ コスト数 の最大値
   - 期待値はコイン依存を確率で、回復・どく・ドロー・エネルギー破壊を換算値で見積もる
2. 総合力で区切る — **キャラクターは 300 / 255 / 225、支援カードは 190 / 115 / 60**（後述）
3. **無色は1段下げる** — 全デッキ共通で2枚積みされ、稀少性が低いため

算出は `tools/rarity.ts` に実装してある。感覚で振らず、必ずこの出力に合わせる。

```
node games/maniwa-tcg/tools/rarity.ts          # 全種別を出す
node games/maniwa-tcg/tools/rarity.ts --diff   # ずれているカードだけ出す（ずれがあれば終了コード1）
```

#### 区切りは種別ごとに、その分布から決める

**アイテム・行動・絶技にキャラの区切りをそのまま当ててはいけない。**
支援カードは HP を持たないので `HP` の項が丸ごと落ちる。キャラの HP は 90〜170、
平均でおよそ 110 あり、これがそのまま下駄になっている。キャラの区切りを流用すると
**どんなに強い支援カードでも全部コモンになる**。

かといって、キャラの区切りから 110 を引いた線を使うのも正しくない。両者は分布の
**形**が違うからである。キャラは HP の下駄で 120〜354 に密集し、支援は -18〜252 に
広く散る。同じ幅の帯を当てても、拾える枚数がまるで変わってしまう。

そろえるのは値ではなく**目標とする形**とする。すなわち
**下のレアリティほど枚数が多くなる**ように、種別ごとに区切りを取る。

| 種別 | 総合力 | UR | SR | R | 内訳 |
|---|---|---|---|---|---|
| キャラクター | `HP + 効率×3 + 最大威力×0.6` | **300以上** | **255以上** | **225以上** | UR8 / SR13 / R21 / C30 |
| 支援カード | `効率×3 + 最大威力×0.6` | **190以上** | **115以上** | **60以上** | UR1 / SR5 / R5 / C13 |

支援カードの内訳は絶技8種を除いた24種のもの。絶技は下の補正で全種 UR になる。

キャラの UR 300 は、ちょうど **EX 8種だけを拾う線**になっている。
「UR は EX 級」という位置づけと一致するので、この値は動かさないほうがよい。

効率の分母は**コスト数**。アイテムと行動はコストが無いので効率＝評価値そのもの、
絶技はエネルギー数で割る。

**絶技は1段上げる。** 対応キャラがバトル場にいるときしか撃てず、そのキャラを積んだ
デッキにしか入らない。無色を「どこにでも入るから1段下げる」としているのと同じ理屈を
逆向きに当てている。強さだけでなく**稀少性**も見る、というこの節の建前を両方向に
効かせるため。この補正により絶技8種はすべて UR になる。

| レアリティ | 表記 | 内部の値 | 種類数 |
|---|---|---|---|
| ウルトラレア | UR | `'ultra'` | 17 |
| スーパーレア | SR | `'superRare'` | 18 |
| レア | R | `'rare'` | 26 |
| コモン | C | `'common'` | 43 |

シミュレーションでレアリティ別の使用率と勝率寄与を出し、**強さの順に単調であること**を
健全性の条件とする。逆転していれば、レアリティか数値のどちらかが実態と合っていない。

| レアリティ | 平均使用率 | 平均勝率寄与 |
|---|---|---|
| UR ウルトラレア | 52.8% | +10.4pt |
| SR スーパーレア | 60.6% | +2.3pt |
| R レア | 52.7% | -0.7pt |
| C コモン | 49.7% | -2.6pt |

（10万戦で測定。カード総数が104種、全カードのレアリティを 8.3 の基準で振り直した時点の値）

### 8.4 バランス調整の記録

初期値では先手勝率が基準を外れていた。原因と対処を残しておく。

| 対処 | 先手勝率 | 備考 |
|---|---|---|
| 初期値 | 73.8% | AI が HP 最大の EX（最安ワザ2エネ）を先発に置き、序盤に殴れなかった |
| AI の先発選択を初撃の速さ優先に | 60.9% | カードデータは不変。後手の初撃が 3.9→2.0 ターンに |
| **HP を一律1.3倍（10刻みに丸め）** | **50.5%** | 試合が 12.1→14.6 ターンに伸び、半ターン差の比重が下がった |
| カードを40種へ量産、水デッキ追加 | 53.6% | 平均15.9ターン（推定3.2分）。3すくみは設計どおり |

先手は後手より常に先に同じエネルギー量へ到達するため、試合が短いほどこの差が効く。
**試合の長さがそのまま先手有利の強さになる**という関係があり、HP はこの調整に使う主なつまみになる。
「先攻1ターン目のエネルギー供給を止める」案も測定したが、先手勝率19.8%と逆に振り切れるため採らない
（エネルギーは自分の手番にしか来ないので、1個減らすと自分のターン2回分の遅れになる）。

**相手側を一段小さくする**のは、8枠すべてを同じ大きさで並べると縦が1200pxを超えて
画面外に出るため。遠近が付くことで「自分の手元が主役」になる副次的な効果もある。

- **バトル場のカードにだけワザを出す。** 「いま何を撃てるか」を長押しせずに読めるようにする。
  ベンチは幅が無く、出すと絵が帯になって誰か分からなくなるので出さない
- **盤面のワザ名にフリガナは振らない。** 132px 幅で2段になると絵が潰れる。
  読みが要るときは長押しで詳細を開く（そちらには 9.1.1 のとおり出る）
- **空きスロットにも盤面カードと同じ寸法クラスを付ける。**
  これが無いと空き枠だけが帯になり、残りの幅を全部吸って隣のカードが潰れる
- **モーダルは `z-index` で盤面より必ず上に置く。** 手札の「選べるカード」に
  `z-index` を与えた結果、手札がモーダルの上に載ってボタンが押せなくなったことがある

### 9.4 引く・出すの動き

カードが手札に増えたとき、盤面に置かれたときに、一度きりの CSS アニメーションを走らせる。

| 対象 | クラス | 動き |
|---|---|---|
| 引いたカード | `.card--draw` | 山札の方向（右下）から滑り込んで実体化する。260ms |
| 置かれたカード | `.card--enter` | 下から迫り上がり、少し行き過ぎてから収まる。300ms |

**実装上の要点。** `renderBattle` は毎回 `root.replaceChildren()` で全部作り直すので、
CSS transition は効かない（比較対象の要素が残らない）。素直にアニメーションを書くと
**再描画のたびに全カードが動く**。そこで前回の描画の手札とインスタンスIDを
`view.ts` のモジュール変数に持ち、**差分に当たるものにだけクラスを付ける**。

- 手札は末尾に増えるので、増えた枚数ぶんの末尾を「引いた」とみなす
- 盤面は前回に無かったインスタンスIDを「置かれた」とみなす
- 同時に複数枚引いたとき（初手の5枚）は 60ms ずつ遅らせ、順に届くように見せる
- この差分は**描画の都合であって状態ではない**ので、`reduce` には持ち込まない（CLAUDE.md 3章）
- 変形は `transform` と `opacity` だけに絞る。レイアウトを動かす性質のプロパティを使うと
  盤面全体の再計算が毎フレーム走る
- `prefers-reduced-motion: reduce` の端末では動かさない。表示そのものは変わらないので、
  アニメーションを消しても情報は失われない


### 9.1 カードの体裁

カード1枚の見た目は、4つの属性をそれぞれ別の視覚要素に割り当てる。
配色は `src/game/theme.ts` に集約し、テンプレート側には色を書かない。

| 要素 | 表すもの | 実装 |
|---|---|---|
| 背景色 | 系統（origin） | `ORIGIN_STYLE`。下側を暗くして文字を載せる |
| 装飾枠 | レアリティ | `RARITY_STYLE.frame`。C 灰 / R 銀 / SR 金 / UR 虹 |
| 色丸に白文字 | 属性（type） | `TYPE_COLOR`。丸の色だけが属性を表し、文字は常に白 |
| カード名・ワザ名の色 | レアリティ | `RARITY_STYLE.text`。C 黒 / R 白 / SR 金 / UR 虹 |

- レアリティは記号ではなく**アルファベット**で書く（C / R / SR / UR）
- 文字色は系統の背景と同化しうるので、`RARITY_STYLE.edge` で縁取りの明度を文字色と逆にする。
  C だけ明るい縁、それ以外は暗い縁になる
- HP・系統名・レアリティ記号のような小さい文字はレアリティ色にせず、白＋暗い影で固定する。
  細い文字にレアリティ色を乗せると潰れて読めない
- UR の虹は枠と文字にグラデーションを使う。文字は `background-clip: text` で切り抜くため
  `text-shadow` が効かず、縁取りは `drop-shadow` に置き換える
- バトル場の印は枠の外側に1段空けてから置く。枠の色（レアリティ）と混ざらないようにする

### 9.1.1 日本語の表記

画面に出る文字は**通常の日本語の正書法**で書く。かな書きに統一しない。

- 漢字で書く語は漢字にする（攻撃 / 逃げる / 手札 / 準備完了 / 毒 / 回復 / 反動）
- 外来語・神名・固有名詞はカタカナ（レーヴァテイン / ヴァジュラ / ミョルニル / テケリ・リ）
- レアリティはアルファベット（C / R / SR / UR）
- 送り仮名・助詞はかなのまま。「入れ替える」を「入替える」にはしない

漢字を使ったカード名・ワザ名には**フリガナを付ける**。`CardDef.ruby` と `AttackDef.ruby`
がその用途で、`undefined` のときは `<ruby>` を作らずそのまま出す（`view.ts`）。
かな書きのままの名前と、カタカナだけの名前にはフリガナを付けない。二重に読ませないため。

```ts
{ name: '神託の矢', ruby: 'しんたくのや', cost: ['light', 'light'], effects: [...] }
{ name: 'レーヴァテイン', cost: ['fire', 'fire'], effects: [...] }   // ruby なし
```

かな書きに寄せると、同音の語（射る/居る、神/紙）が読み取れず、行の折り返しも増える。
DotGothic16 は漢字の字形が整っているので、漢字のほうが小さい字でも判別しやすい。

### 9.2 カードイラスト

`src/data/art/<カードid>.webp` に置くと `src/game/art.ts` が自動で拾う。
ファイル名がカードとの結び付けなので、絵を足すときにデータもロジックも触らない。

- 形式: WebP（画質 0.80）/ 正方形 / **1024×1024**（1枚あたり約145KB、248枚で約36MB）
  - 詳細画面での表示は最大 364px 角（`.app` の 480px と modal の 420px で頭打ち）。
    Android の DPR は 2.6〜3.5 が多く、実ピクセルでは約 950〜1270px を要求される。
    1024 でほぼ等倍になる
  - 512 では髪や装飾がはっきり甘くなる（実表示サイズで比較して確認済み）。
    1024 の画質 0.80 と 0.85 は見分けがつかないため、軽い 0.80 を採る
  - 絵は長押しで1枚ずつ読むだけなので、初期表示の重さには影響しない
  - **生成は短辺 1024px 以上で行う。** それ未満だと切り出し後に 1024 に届かず、
    引き伸ばしても情報は増えないのでそのまま小さく格納される
- **1キャラにつき3枚**（通常・ダメージ1・ダメージ2）必要になる。40種で120枚、約12MB
- 未配置のカードは、属性の丸だけを置いた枠で代用する。絵が揃うまで表示は壊れない
- 外部で生成した絵を取り込む場合も、正方形に切り出して WebP にするだけでよい

生成AIに渡す入力は `tools/art-brief.ts` が書き出す。渡すのは以下の5項目だけとする。

| 項目 | 用途 |
|---|---|
| カードID | 出来上がった絵のファイル名（`<カードid>.webp`） |
| カード名 | 描く対象 |
| 系統 | 神話ごとの意匠・文様・色調の指定 |
| レアリティ | 描き込み量と構図の格 |
| 解説 | 姿・持ち物・場面の根拠 |

タイプ・HP・ワザは**渡さない**。数値を見せると絵がそれに引きずられ（炎タイプだから
燃やす、HPが高いから大きい）、解説と食い違う画になるため。属性は色丸で別途示すので、
絵の側で重ねて表す必要もない。

```bash
node tools/art-brief.ts            # 全40種
node tools/art-brief.ts f002 g006  # IDを指定
node tools/art-brief.ts --json     # JSON
```

### 9.3 ダメージイラスト

1枚のカードにつき絵を3枚持ち、傷み具合で差し替える。同じ美少女の、無傷・傷ついた姿・
追い詰められた姿を描く。

| 段階 | 条件 | ファイル名 |
|---|---|---|
| 通常 | ダメージ0 | `<カードid>.webp` |
| ダメージ1 | ダメージを受けている（残りHPが半分より上） | `<カードid>-d1.webp` |
| ダメージ2 | **残りHPが半分以下** | `<カードid>-d2.webp` |

- 判定は `artStage(hp, damage)`（`src/game/art.ts`）。表示だけの段階で、ルールには関与しない。
  ダメージ計算・きぜつ判定は一切変わらない
- 半分**以下**でダメージ2に入る。HP90 なら残り45でダメージ2
- 未配置のときは1段ずつ手前に戻る（d2 が無ければ d1、d1 も無ければ通常、それも無ければ
  属性の丸だけの代替表示）。3枚揃っていないカードがあっても表示は壊れない
- 絵は**盤面のカードにも敷く**。詳細を開かなくても、傷んだことが対戦中に分かるようにする
- 手札は場に出ていないので常に通常の絵を使う

## 11. テスト方針

`games/maniwa-tcg/tests/` に置き、**core のみを対象**とする（CLAUDE.md 2章）。

### 必須テスト（CLAUDE.md 5章）

| テスト | 内容 |
|---|---|
| **決定論リプレイ** | 同一シード + 同一 Action 列を2回流し、`hashState` の完全一致を確認する。途中の全ステップでも比較する |
| **ルール不変条件** | 全ステップで以下を検査: `damage >= 0` / `points >= 0` / 手札・山札・トラッシュ・場の合計が常に20 / ベンチ ≤ 3 / `attached.length >= 0` / いずれの数値も `NaN` でない |
| **終局保証** | 無限ループの検出。2水準で確認する（下記） |

終局保証は目的が「無限ループの検出」なので、水準を2つに分ける。

| AI | 基準 |
|---|---|
| ランダムAI 1万回 | すべてが**有限ステップで終了する**（ターン上限による打ち切りを含む） |
| 貪欲AI 1万回 | すべてが **`MAX_TURNS` 未満で決着する**（打ち切り率0%） |

ランダムAIは無意味な手を選び続けるためターン上限に届くことがあるが、それは
無限ループではない。上限到達を許さない基準は、まともに打つ側（貪欲AI）に課す。

### その他

- `legalActions` が返す Action は必ず `reduce` で受理される（拒否ログが出ない）
- `legalActions` が空になるのは `phase.kind === 'ended'` のときだけ
- 先攻1ターン目に `attack` が `legalActions` に含まれない
- 弱点 +20、EX の2ポイント、どくの10ダメージの個別検証
- `reduce` は入力 `state` を書き換えない（凍結オブジェクトを渡して検証）

## 12. シミュレーション指標

`games/maniwa-tcg/tools/sim.ts`。`npm run sim -- maniwa-tcg` で実行される。
**1万回**の自動対戦を行い、以下を出力する。基準を外れても**報告のみ**とし、独断でカードデータを書き換えない（CLAUDE.md 5章）。

### 必須項目

| 指標 | 基準 |
|---|---|
| 先手勝率 | **45〜55%**。逸脱したら要調整。**ミラーマッチで測定する**（8.2） |
| 平均ターン数 | 併せて中央値・最小・最大・分布を出す |
| 平均試合時間 | ①シミュレータ実行時間(ms/試合) ②推定プレイ時間 = ターン数 × 12秒（想定値、要確認 Q4） |
| カード別の採用率 | デッキに入っていた試合の割合 |
| カード別の勝率寄与 | そのカードを**使用**した試合の勝率 − 全体勝率 |
| 未使用カード一覧 | **1万回で一度も使われなかったカード**を全件列挙する |

### 追加で出す項目（バランス調整の判断材料）

- 引き分け率、`MAX_TURNS` 到達率（**0% であること**。終局保証と対になる）
- 決着理由の内訳（`points` / `noCreature` / `turnLimit` / `simultaneous`）
- 平均獲得ポイントと、EX きぜつが決め手になった試合の割合
- 攻撃別の使用回数と平均ダメージ
- にげる使用率、エネルギー付与の平均回数、余剰エネルギー（使われずに終わった数）
- 先攻/後攻それぞれの平均ターン数
- デッキ相性（対戦組み合わせごとの勝率）
- 使用シードと試合数（再現用）

### デッキモード（3.1.1）

`--decks=fixed`（既定）で基準デッキ、`--decks=pool` でプールデッキを使う。

| モード | 見るもの | 注意 |
|---|---|---|
| `fixed` | 先手勝率・ターン数・デッキ別平均勝率のレンジ・基準デッキ内のカード寄与 | **上の基準値はこちらのみに適用する** |
| `pool` | プール全体のカード別採用率と勝率寄与、未使用カードの検出、**レアリティの健全性** | デッキが毎試合変わるので、先手勝率とレンジは基準として使わない |

**レアリティの単調性（8.3 の健全性条件）は `pool` で判定する。**
`fixed` のレアリティ表は「デッキに入ったカード」しか数えられず、基準デッキは固定なので
**あとから足したカードは一度もこの検査を通らない**。落とした種類数は表に出るようにして
あるので、`（+N種 デッキ未採用で対象外）` が出ていたら pool を見ること。

`pool` はデッキ構成が試合ごとに変わるため、**デッキ相性とレンジに意味が無い**。
逆に `fixed` は基準デッキに入っていないカードを一切測れない。両方を出して使い分ける。

### 個別カードの価値測定

`tools/card-value.ts <カードID>` で、そのカードの価値を基準デッキ上で測る。
基準デッキの同種別の1枠を対象カードに差し替え、差し替え前後で勝率寄与を比べる。

新しく足したカードが既存の何と比べて強いのかは、プール全体の平均では分からない。
「この枠をこのカードに替えたら何pt動くか」が要る。夜間ジョブが毎晩スクリプトを
書き捨てて同じことをしていたので、再現可能な形に固定した。

### 出力形式

人が読むテキストサマリを標準出力へ。あわせて機械可読な JSON を任意で出力できるようにする（`--json` オプション）。CI では終了コードのみを見る。

## 14. 決定事項と推奨案

### 14.1 決定済み（全件承認済み）

| # | 論点 | 決定 |
|---|---|---|
| **Q1** | 先攻1ターン目のエネルギー供給 | **供給する**。先攻1ターン目に禁止されるのは攻撃のみ |
| **Q2** | 両者が同時に3ポイントに達した場合 | **手番プレイヤー（攻撃した側）の勝ち** |
| **Q3** | 初期配置でベンチに出せる数 | **最大3体まで同時に出せる** |
| **Q4** | 「平均試合時間」の定義 | **推定プレイ時間を主指標**とし、実行時間も併記。目標は1試合3〜5分 |
| **Q5** | v1 の対戦相手 | **CPU のみ** |
| **Q6** | 題材の扱い | **ルールの骨格のみ原作に倣い、カード名・キャラクターは世界の神話8系統をモチーフにする** |

Q1 の帰結として、先攻はエネルギー1個ぶん先行する。先手勝率が55%を超えた場合、
**最初の調整候補は「先攻1ターン目はエネルギーを供給しない」へのルール変更**とする。
カードデータの書き換えではなくルール側の調整なので、12章の報告に含めて判断を仰ぐ。

### 14.2 各決定の理由

#### Q2: 同時に3ポイント到達 → 手番プレイヤーの勝ち

`selfDamage` の反動で自分の EX が同時にきぜつする、といった稀なケースで起こりうる。

- 「3ポイント先取」は必ず決着することを狙った設計であり、引き分けはその目標と衝突する
- 反動を持つカードは「リスクを取って勝ちを狙う」設計意図で作る。同時到達で勝てないと、そのカード設計自体が成立しない
- 実装は勝敗判定で手番プレイヤーを先に評価するだけで済み、分岐が1本減る
- 引き分け自体はターン上限（3.6 の4番）で必要なので、表示・集計の実装は結局必要になる。Q2 を引き分けにしても実装は簡単にならない

原作準拠なら引き分けだが、v1 は決着優先を採る。発生率は12章で計測して報告する。

#### Q3: 初期配置でベンチに最大3体 → 同時に出せる

- ベンチが空の状態で始まると、バトル場がきぜつした瞬間に敗北（3.6 の3番）となり、事故負けが増える。先手勝率が事故率に飲まれて指標として読めなくなる
- 1体ずつしか出せない仕様にすると、序盤が「場を作るだけのターン」で埋まりテンポが落ちる。1試合3〜5分（Q4）に収めるうえで不利
- 実装は `setupPlace` を繰り返し受け付けるだけで、追加の状態を持たない

#### Q4: 平均試合時間 → 推定プレイ時間を主指標に

- CLAUDE.md 5章がこの指標を求める意図は「1試合が人にとって長すぎないか」の監視にあると解釈する。したがって推定プレイ時間が本命
- 実行時間（ms/試合）は CI での性能退行検知に使える副産物なので併記する
- **1ターン12秒という係数には根拠が無い**。v1 が実機で遊べるようになった時点で実測し、係数を更新する。それまでは暫定値と明記して出力する

#### Q5: v1 は CPU のみ

- バーティカルスライスを1本完成品質で通すのが v1 の目的（CLAUDE.md 7章2項）
- 同一端末での2人対戦は、手札を隠すための目隠し画面と受け渡しの導線が必要になり、UI 工数が大きく増える。ルールの完成度に使うべき時間を奪う
- CPU は `tools/ai.ts` をそのまま流用でき、シミュレーションと実装を共有できる。ルールの二重実装が発生しない
- 対戦相手の追加は Action の発行元を差し替えるだけなので、v2 で低コストに入れられる

#### Q6: カード名・キャラクターは独自のものにする

- ゲームのルールやシステムそのものは著作権の保護対象ではないため、骨格を原作に倣うことに問題はない
- 一方でポケモンの名称・キャラクターデザイン・イラストは権利物であり、静的ビルドに含めて配布・公開するとリスクになる
- 独自名なら配布・公開・スクリーンショット共有を制約なく行える
- モチーフは**世界の神話8系統**（日本・エジプト・北欧・インド・中東・クトゥルフ・ギリシア・中国）とする。
  神名・伝承上の名はいずれも権利の対象ではない。炎＝火と太陽と破壊、草＝大地と豊穣と蛇、無色＝眷属という
  対応が型ごとの性格づけとそのまま噛み合い、系統ごとに2枚ずつ配ることでカード量産時の指針にもなる
  （8章の3枚はこの方針で作成済み）

  クトゥルフ神話は20世紀の創作を出発点とするが、中核となる神格の名称は現在パブリックドメインにある。
  ただし後発の作品に固有の設定・固有名は取り込まないこと

## 16. カード種別の拡張

クリーチャーだけだった `kind` を4種類に広げた。Q7〜Q12 は承認済み（16.8）。
**Q11 のみ「枚数の制限は設けない」に変更**。デッキに入れる非クリーチャーの枚数は自由で、
クリーチャーを1枚以上入れること（3.1）だけが条件になる。

### 16.1 4つの種別

表示名と `kind` の値は切り離してある。`kind` はコード上の識別子で、
セーブデータにも入るため**変更しない**。表示名だけを変えるときは
`src/game/view.ts` の `KIND_LABEL` を直す。

| 種別（表示名） | `kind` | 1ターンの使用回数 | コスト | 使用後 |
|---|---|---|---|---|
| 姫神 | `'creature'` | 場に出す（ベンチ空きぶん） | なし | 場に残る |
| 神具 | `'item'` | **制限なし** | なし | トラッシュ |
| 道標 | `'action'` | **1枚まで** | なし | トラッシュ |
| 絶技 | `'ultimate'` | **1回（攻撃と排他）** | エネルギー | トラッシュ |

- **姫神（ひめがみ）** — 神格を美少女として擬人化した本体。場に出して戦わせる
- **神具（じんぐ）** — 手札とエネルギーを回す潤滑油。効果は小さく、事故を減らす役
- **道標（みちしるべ）** — 1ターン1枚の強い一手。盤面を動かす（入れ替え・大回復・山札から連れてくる）
- **絶技（必殺技）** — 特定の姫神が**バトル場にいるときだけ**撃てる切り札。
  エネルギーを払い、**撃つとターンが終了する**。攻撃の代わりに使う一撃であって、
  攻撃に上乗せするものではない。先攻1ターン目に撃てないのも攻撃と同じ

### 16.2 スキーマ

`CardDef` を種別ごとの直和にする。共通項（id / name / flavor / origin / rarity）は残し、
キャラクター専用の項目（hp / type / ex / weakness / attacks / retreatCost）は
`kind: 'creature'` のときだけ持つ。こうすると「アイテムの HP」のような無意味な状態を
型で作れなくなる。

```ts
interface CardBase {
  readonly id: CardId
  readonly name: string
  readonly flavor: string
  readonly origin: Origin
  readonly rarity: Rarity
}

export type CardDef =
  | (CardBase & {
      readonly kind: 'creature'
      readonly type: EnergyType
      readonly hp: number
      readonly ex: boolean
      readonly retreatCost: number
      readonly weakness: EnergyType | null
      readonly attacks: readonly AttackDef[]
      readonly stage?: 0
      readonly evolvesFrom?: string
    })
  | (CardBase & { readonly kind: 'item';   readonly effects: readonly Effect[] })
  | (CardBase & { readonly kind: 'action'; readonly effects: readonly Effect[] })
  | (CardBase & {
      readonly kind: 'ultimate'
      /** この絶技を撃てるキャラ。バトル場にいることが条件 */
      readonly requires: CardId
      readonly cost: readonly EnergyType[]
      readonly ruby?: string
      readonly effects: readonly Effect[]
    })
```

効果は**すべて既存の `Effect` で表す**（CLAUDE.md 4章）。種別ごとに関数を書かない。

### 16.3 追加する Effect

既存9種では表せないものだけを足す。解釈は `core/effects.ts` の1箇所に増やす。

```ts
/** エネルギーゾーンに1つ足す（今ターンの在庫が埋まっていれば次ターンぶん） */
| { readonly type: 'gainEnergy'; readonly value: number }

/** 対象にエネルギーを直接つける。付与フラグを消費しない */
| { readonly type: 'attachEnergy'; readonly target: Target; readonly value: number }

/** 相手のバトル場をベンチの1体と入れ替える（PRNG使用） */
| { readonly type: 'switchOpponent' }

/** 山札からクリーチャーを1枚手札に加えてシャッフル（PRNG使用） */
| { readonly type: 'searchCreature' }
```

`Target` に `'ownBenchAll'`（自分のベンチ全体）を足す。全体回復を書くため。

### 16.4 状態と Action の追加

```ts
// PlayerState
readonly usedActionThisTurn: boolean   // 行動カードを使ったか
readonly attackedThisTurn: boolean     // 攻撃または絶技を使ったか（既存の判定を明示化）

// Action
| { readonly type: 'playItem';     readonly player: PlayerId; readonly handIndex: number }
| { readonly type: 'playAction';   readonly player: PlayerId; readonly handIndex: number }
| { readonly type: 'useUltimate';  readonly player: PlayerId; readonly handIndex: number }
```

`legalActions` がこの3つも返すようにする。UI・AI・シミュレータは今までどおり
`legalActions` だけを見るので、どれも判定を書き足さない（SPEC 9章）。

### 16.5 デッキ構築の制限

- 20枚ちょうど / 同名2枚まで は据え置き
- **非クリーチャーの枚数に上限は設けない**（Q11）。クリーチャーを1枚以上入れること
  （3.1）だけが条件
  - ただしクリーチャーが極端に少ないと、初手にクリーチャーが来ず引き直しが続く。
    10回失敗するとデッキ不正としてエラー終了する（3.2）。プリセットは14枚積んでいる
- 絶技は、対応するキャラが同じデッキに入っていなければデッキ不正とする
  （`validateDeck` で検査する）

#### 16.5.1 絶技の強さは「エネルギー1つあたり」で決める

絶技を作るときは、対応する姫神の最強ワザと**1エネルギーあたりの評価値**で比べ、
**1.05〜1.30 倍**に収める。`tools/ultimate-check.ts` が検査する。

```
効率 = 効果の評価値 ÷ コスト数
比   = 絶技の効率 ÷ 対応姫神の最強ワザの効率      → 1.05〜1.30
```

**この帯は実測から引いた。** pool 3万戦での使用率と並べると境界がはっきり出る。

| 効率比 | 使用率 | |
|---|---|---|
| 0.857 | **1.3%** | 死に札（2026-08-23 の未採用案） |
| 1.095〜1.250（既存10種） | 19.5〜35.7% | 健全 |

境界は 0.857 と 1.095 のあいだにある。両側に余裕を取って 1.05〜1.30 とした。
下限を 1.10 にすると `u004 地底の眠り`（比1.095・実測32%で健全）を誤って弾く。

**「最強ワザより評価値で +10〜+20」という基準は使わない。**
コストを見ていないため、**基準を満たすのに撃つ価値が無いカードが通ってしまう**。

実際に2度、この穴で死に札を作っている。

| | 絶技 | 対応姫神の最強ワザ | 効率比 | 結果 |
|---|---|---|---|---|
| 2026-08-19 `u003 黄の印` | コスト3 | コスト3 | 1.00 | 使用率ほぼ0。威力を上げて修正 |
| 2026-08-23（未採用） | コスト3・評価77 | **コスト2**・評価60 | **0.86** | 使用率 1.3%。設計をやり直し |

絶技は**撃つとターンが終わる**（16.1）。通常攻撃の代わりに使う一撃なので、
1エネルギーあたりで通常攻撃に劣るなら、AI も人も撃たないのが正しい判断になる。
raw の差だけ見ていると、この当たり前が見落とされる。

#### 16.5.2 実質的に「絶技は EX 姫神に付ける」ことになる

16.5.1 の比を満たせるのは、**対応姫神の最強ワザがコスト3のとき**にほぼ限られる。
最強ワザがコスト2なら、コスト3の絶技は効率で不利になるため、比を満たすには
評価値を大きく上げるしかなく、今度はカードが強すぎる。

現在の分布は次のとおり。

```
EX 姫神:  最強ワザ コスト3 → 9体 / コスト2以下 → 0体
非EX姫神: 最強ワザ コスト3 → 6体 / コスト2以下 → 60体
```

**EX は全員がコスト3**なので、EX に付ければ自然に条件を満たす。
これが「絶技は EX に付ける」という慣習の正体であり、飾りではなく機能上の要請である。

型の上では `UltimateCard.requires` にどの姫神でも指定できる。**非EXに付けるなら、
その姫神の最強ワザがコスト3であることを必ず確認する**こと（現在は6体のみ）。

**この制約の副作用**として、中国・エジプト・インド・中東の4系統には絶技を作れない。
この4系統には最強ワザがコスト3の姫神が1体もいないためである。埋めるなら、
先にこれらの系統へ**最強ワザがコスト3の姫神を追加する**必要がある。

#### 16.5.3 無属性の姫神には絶技を付けない

`UltimateCard.requires` に**無属性（colorless）の姫神を指定してはならない。**

無属性は全8デッキに2枚ずつ入る共通枠なので、そこに絶技を付けると
**どの属性のデッキからでも同じ絶技が撃てる**。絶技を「そのデッキ固有の切り札」に
している 16.5 の前提が崩れる。これが設計上の理由。

**加えて、破ると機能しない。** プールデッキの抽選（`src/data/pool-decks.ts`）は
絶技の候補を**デッキの属性の姫神からしか探さない**。

```ts
const mainPool = CREATURES.filter((c) => c.type === type)
const ultimatePool = ULTIMATES.filter((u) => mainPool.some((c) => c.id === u.requires))
```

無属性の姫神は `mainPool` ではなく `neutralPool`（共通枠）から取り、`POOL_TYPES` に
`colorless` は入っていない。したがって**無属性を要求する絶技は、どのシードでも
一度も選ばれない**。プールデッキ上では完全な死に札になる。

現在この条件を満たしてしまう姫神は **n003 タオテツ（中国・無属性・最強ワザがコスト3）**
の1体だけ。中国は絶技0種なので「系統の穴を埋められる唯一の候補」に見えるが、
**選んではならない。**

`tests/ultimates.test.ts` がこれを検査する。`tools/ultimate-check.ts`（効率比）と
`tools/rarity.ts` は**どちらもこの違反を検出しない**ので、テストが唯一の防波堤になる。

> 2026-08-27 の夜間ジョブが実際にここを踏んだ。効率比もレアリティも通り、
> `card-value.ts` では寄与 +12.0pt と良好だったが、プールデッキのテストが落ちた。
> 個別のカード検査だけでは気付けないため、条件を明文化して機械で見る形にした。

- **シミュレーション** — 先手勝率45〜55%を維持すること。種別ごとの採用率・勝率寄与を

- 絶技はキャラ依存なので、**絶技だけが使われずに終わっていないか**を必ず見る

## 17. 属性の拡張

属性を3種（炎・草・水）＋無色から、**8種＋無**に広げた。Q13〜Q17 は承認済み（17.7）。

### 17.1 属性の一覧

| 系列 | 属性 | 内部の値 | 相性 |
|---|---|---|---|
| 元素6種 | 炎 / 水 / 森 / 土 / 風 / 雷 | `fire` `water` `forest` `earth` `wind` `thunder` | 環（17.2） |
| 対の2種 | 光 / 闇 | `light` `dark` | 互いにだけ |
| 例外 | 無 | `colorless` | **どことも相性を持たない** |

`grass` は `forest` に改名する。元素の並びとして「草」だけ植物名なのは座りが悪い。
既存カードのデータ変更が要るので、承認が取れた時点でまとめて行う。

**無は現行の `colorless` をそのまま使う。** すでに「弱点を持たず、弱点を突くことも
できない」挙動になっており、求められている「どこにも相関しない属性」と一致する。
コストは任意の属性1つで支払え、無エネルギーそのものは供給されない（現行どおり）。
つまり無のキャラはどのデッキにも入れられる、相性の外側の枠になる。

### 17.2 相性

**元素6種は環にする。各属性は「環の次の1つ」に強い。**

```
炎 → 森 → 風 → 土 → 雷 → 水 → 炎（先頭に戻る）
```

| 攻撃側 | 弱点を突ける相手 | 根拠 |
|---|---|---|
| 炎 | 森 | 森を焼く |
| 森 | 風 | 木立が風を受け止める |
| 風 | 土 | 砂を巻き上げ、地を削る |
| 土 | 雷 | 地に雷を逃がす |
| 雷 | 水 | 水を伝って焼く |
| 水 | 炎 | 炎を消す |

隣1つにすると、不利対面は 1/6 = **17%**。今の3すくみ（1/3 = 33%）の半分になり、
対面が決まった時点で勝敗が見える状況が減る。隣2つにすると 2/6 = 33% で今と変わらず、
属性を増やした効果が出ない。

**光と闇は互いにだけ弱点を持つ。** 元素6種とは相性を持たない（どちらからも +0）。
**無はどの属性とも相性を持たない。** 突くことも突かれることもない。

### 17.3 光・闇の調整

光と闇は「不利対面が1属性しか無い」ため、そのままでは元素より一方的に得をする。
これを打ち消すために、**光・闇どうしの弱点ボーナスだけを大きくする**。

| 組み合わせ | ボーナス |
|---|---|
| 元素どうし（環で有利） | +20（現行と同じ） |
| 光 ⇄ 闇 | **+40** |

光闇は「元素にはめっぽう強いが、同族と当たると一撃で崩れる」ハイリスクな枠にする。
数値は実測で決める。まず +40 で測り、光闇の勝率が突出するなら上げる。

### 17.4 相性の実装

現在 `CardDef.weakness` は「弱点となる属性1つ」を持つ。環はデータではなく
**`core/types.ts` の表として1箇所に置く**（`WEAKNESS_CHART`）。カードごとに手で
書くと、環と食い違ったカードが必ず出る。

```ts
/** 攻撃側の属性 -> 弱点を突ける相手の属性 */
export const WEAKNESS_CHART: Readonly<Record<EnergyType, readonly EnergyType[]>> = {
  fire: ['forest'], forest: ['wind'], wind: ['earth'],
  earth: ['thunder'], thunder: ['water'], water: ['fire'],
  light: ['dark'], dark: ['light'],
  colorless: [],   // 無はどこにも相関しない
}
```

カード側の `weakness` は表から導出できるので**廃止する**。

### 17.5 必要なカード数

エネルギーを供給できる属性は8種（元素6 + 光 + 闇）。無は供給されないので、
どのデッキにも入る共通枠になる。単色デッキには1属性あたりキャラ6種以上が要る
（6種×2枚 + 無2枚 = 14枚）。

| 種別 | 実装済み |
|---|---|
| 属性キャラ | **64**（8属性 × 8） |
| 無キャラ | **8** |
| キャラ合計 | **72** |
| アイテム / 行動 / 絶技 | 12 / 12 / 8 |
| カード総数 | **104** |

プリセットは属性ごとに1デッキ、計8デッキ。1デッキ20枚の内訳は
「専用キャラ8種×1 + 無4種×1 + アイテム3 + 行動3 + 絶技1種×2」。
104枚すべてがどこかのデッキで使われる。

### 17.6 デッキの地力は支援カードの配り方でほぼ決まる

属性を8種にしたあと、8デッキの総当たり平均勝率は **27.6pt** 開いていた。
原因を追うと、キャラの数値ではなく**アイテムと行動の割り当て**だった。

- 弱点ボーナスを0にしても差は縮まらない（23.4pt）。相性の環は原因ではない
- 最弱だった「かぜ」に最強の「やみ」のキャラをそのまま入れても 41.6% のまま。
  **キャラではなく枠が弱かった**
- 支援カードを配り直すと、同じキャラのまま 38.6% → 58.2% に動いた

支援カードは1枚あたりの効きがキャラより大きい。とくに**エネルギー加速**が強く、
`tools/ai.ts` の重み付けではこれを安く見積もっていたため、点数をそろえても
勝率は開いたままだった（手で付けた重みは実際の強さを言い当てられない）。

最終的に、組み合わせを多数試して**実測でもっともそろう配分**を選んだ。
現在のレンジは **14.1pt**。

| デッキ | 平均勝率 |
|---|---|
| いかずち | 58.1% |
| ひかり | 55.6% |
| みず | 52.1% |
| もり | 51.5% |
| かぜ | 48.1% |
| やみ | 46.6% |
| つち | 44.1% |
| ほのお | 44.0% |

**残りの14.1ptは未解決**。支援カード1枚ずつの実効値を測る仕組み（同じデッキで
支援だけ差し替えて比較する）が無いと、これ以上は手探りになる。12章の指標に
「デッキ別の平均勝率とそのレンジ」を足し、基準を決めるところから必要。

### 17.6.1 相性の偏りは弱点のせいではなかった

16章の実装後に「デッキ相性が極端（ほのお・日輪 vs くさ・叢雲 が 96.6%）」と
報告したが、弱点ボーナスを 0 にして測り直したところ **89.1%** だった。
偏りの大半は弱点ではなく**デッキの地力の差**である。

| 対面 | 弱点あり | 弱点なし | 弱点の寄与 |
|---|---|---|---|
| ほのお・日輪 vs くさ・叢雲 | 96.6% | 89.1% | 7.5pt |
| ほのお・日輪 vs くさ・世界樹 | 92.1% | 66.5% | 25.6pt |
| くさ・叢雲 vs みず・世界蛇 | 46.2% | 15.4% | −30.8pt |

「くさ・叢雲」は絶技を積めていない（草に紐づく絶技が1種しか無いため）ぶん弱く、
弱点の有利がその弱さを覆い隠していた。**属性を増やしても、この差は縮まらない。**
デッキの地力をそろえる作業は、属性の拡張とは別に必要になる。
