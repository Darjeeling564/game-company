# maniwa-duel 仕様書

**姫神戦記（きしんせんき）** — 遊戯王デュエルリンクス（スピードデュエル）の骨格を借りた
1対1のカードバトル。

`maniwa-tcg`（姫神演義）とは**別のゲーム**である。ルールは共有しない。
共有するのは**カードイラストだけ**（2章）。`maniwa-tcg` 側は1バイトも変更しない。

---

## 0. このゲームを作る理由

`maniwa-tcg` はポケモンカードゲームポケット型（デッキ20枚 / バトル場1＋ベンチ3 /
エネルギー自動供給 / ポイント先取）である。デュエルリンクスは**遊戯王側の同じ位置**にあり、
本家を携帯向けに削ったもの同士なので、発想の階層がそろう。

すでに **288枚のイラスト**と **87体の姫神**という世界観の資産がある。
これを別のルールで動かす。

### 元にした規則の確度

2026-09-25 に調べた。**確認できたものと、できなかったものを分けて記録する。**

| 項目 | 値 | 確度 |
|---|---|---|
| ライフポイント | 4000 | 確認済み |
| 盤面（片側） | モンスター3 / 魔法罠3 / フィールド1 | 確認済み |
| メインデッキ | 20〜30枚 | 確認済み |
| 初期手札 | 4枚。先攻1ターン目はドローしない | 確認済み |
| **メインフェイズ2** | **無い** | 確認済み（本家との最大の違い） |
| 手札上限 | エンドフェイズに6枚 | 確認済み |
| エクストラデッキ | 上限9枚（ミッションで解放） | 初期値が 5 か 6 か情報が割れた |
| 召喚法の追加 | シンクロ＝5D's / エクシーズ＝ZEXAL / ペンデュラム＝ARC-V / リンク＝VRAINS | 順序のみ確認。日付は取れず |
| 制限時間 | ターン制ではなく**時間制**。1ターン3〜4分＋通算の持ち時間 | 確認済み |
| 時間切れの勝者 | — | **確認できなかった** |

**このゲームは正確な再現を目標にしない。** 個人で遊ぶためのものなので、
上の表で埋まらなかったところは自分たちで決める。

## 1. v1 スコープ

CLAUDE.md 7章の「バーティカルスライス優先 — 全機能を薄く作らず、最小構成を完成品質で1本通す」
に従う。

### v1 に含む

- 通常召喚 / セット / リリース（生贄）召喚
- 攻撃表示 / 表側守備表示 / 裏側守備表示
- バトル（攻撃宣言・戦闘ダメージ・戦闘破壊・ダイレクトアタック）
- 魔法（**神具と絶技**）の発動、罠（道標）のセットと**バトル中の割り込み1段**
- ライフ4000・デッキ切れ・ターン上限による決着
- CPU 対戦（貪欲法）
- **ライフに連動するダメージイラスト**（9.3）
- 2属性ぶんの姫神とプリセットデッキ2つ

### v1 に含まない（v2 以降）

| 項目 | 理由 |
|---|---|
| エクストラデッキ（融合・シンクロ・エクシーズ・ペンデュラム・リンク） | 姫神87体はレベルとリリースだけで回せる。EMZ とリンク先の規則は v1 に不要 |
| **スキル** | デュエルリンクス固有の要素だが、決闘が1本通ってから乗せる。**絶技を充てる案は取り下げた**（6.3） |
| **通常魔法・通常罠以外の魔法罠** | 永続・装備・フィールド・速攻・カウンター。**型だけ用意して実装しない**（6.4）。v1 の魔法はすべて通常魔法、罠はすべて通常罠 |
| チェーン2段以上 | 11章。v1 は1段 |
| 8属性すべてのデッキ | ロジックとテストが安定してから（CLAUDE.md 7章5） |
| 時間制限 | 1人で遊ぶので不要。終局保証はターン上限で行う（3.7） |

## 2. カードイラストは maniwa-tcg と共有する

**複製しない。** `games/maniwa-tcg/src/data/art/` を相対参照する。

```ts
// games/maniwa-duel/src/game/art.ts
const FILES = import.meta.glob('../../../maniwa-tcg/src/data/art/*.webp', {
  eager: true, query: '?url', import: 'default',
})
```

288枚・約43MB を git に重複させないためである。

**引き換えに結合が生まれる。** `maniwa-tcg` 側で `src/data/art/` を移動・改名すると
このゲームが壊れる。**この一点だけは両ゲームの間の約束**として、
`games/maniwa-duel/src/game/art.ts` の冒頭と `games/maniwa-tcg/src/data/art/README.md`
の両方に書く（README への追記は `maniwa-tcg` の変更になるため、**実装時に承認を取る**）。

カードIDは `maniwa-tcg` と同じものを使う（`f001` = カグツチ）。
**イラストとIDの対応を崩さないため**で、これにより `art-files.ts` の進捗集計も共用できる。

## 3. ルール

### 3.1 デッキ構築

- **20枚ちょうど**
- 同名カードは**2枚まで**（`maniwa-tcg` と同じ。デュエルリンクスは3枚だが、
  カードプールが2枚制限を前提に作られているのでそろえる）
- エクストラデッキは無い（v1）

推奨の内訳（プリセットデッキ）:

| 種別 | 枚数 |
|---|---|
| 姫神（モンスター） | 11 |
| 神具・絶技（魔法） | 5 |
| 道標（罠） | 4 |

### 3.2 盤面

片側につき:

- **モンスターゾーン 3**
- **魔法罠ゾーン 3**
- デッキ / 手札 / 墓地
- ライフポイント **4000**

### 3.3 ゲーム開始

1. 両者のデッキをシャッフル（シード付きPRNG）
2. 先攻を決める
3. 両者が**4枚**引く
4. **先攻1ターン目はドローしない**
5. **先攻1ターン目はバトルフェイズを行えない**（本家と同じ）

引き直し（マリガン）は**行わない**。`maniwa-tcg` では初手に置けるカードが無いと詰むため
導入したが、こちらは場に何も出せなくてもターンを渡せるので詰まない。

### 3.4 ターン進行

```
ドローフェイズ → メインフェイズ → バトルフェイズ → エンドフェイズ
```

**メインフェイズ2は無い。** 罠と魔法はバトルに入る前に置ききる必要がある。
これはデュエルリンクスで確認できた仕様で、**このゲームの手触りを決める中心**である。

| フェイズ | できること |
|---|---|
| ドロー | デッキから1枚引く（先攻1ターン目を除く）。デッキが空なら**敗北** |
| メイン | 通常召喚/セット（**1ターンに1回**）/ 表示形式の変更 / 魔法の発動 / 罠のセット |
| バトル | 攻撃宣言。1体につき1回 |
| エンド | 手札が**6枚**を超えていたら超過分を捨てる |

### 3.5 召喚

通常召喚は**1ターンに1回**。レベルでリリース（生贄）が要る。

| レベル | リリース |
|---|---|
| 1〜4 | 不要 |
| 5〜6 | 1体 |
| 7以上 | 2体 |

- **セット**（裏側守備表示で置く）も通常召喚1回を消費する
- リリースしたモンスターは墓地へ
- **召喚したターンは表示形式を変更できない**
- 表示形式の変更は1ターンに1回まで

### 3.6 バトル

- 攻撃できるのは**攻撃表示のモンスターだけ**。1体につき1回
- **召喚したターンでも攻撃できる**（本家と同じ）
- 相手のモンスターゾーンが空なら**ダイレクトアタック**（攻撃力ぶんライフを削る）

戦闘の計算:

| 相手 | 結果 |
|---|---|
| 攻撃表示 | 攻撃力が低いほうが破壊され、**差が破壊された側のライフへ**。同値なら両方破壊・ダメージ無し |
| 表側守備表示 | 攻撃力 > 守備力 → 破壊のみ（**ダメージ無し**）。攻撃力 < 守備力 → **攻撃側が差を受ける**。同値なら何も起きない |
| 裏側守備表示 | **表にしてから**上と同じ |

貫通は v1 では作らない。

### 3.7 勝敗

| 決着 | 条件 |
|---|---|
| `lifePoints` | どちらかのライフが **0以下** |
| `deckOut` | ドローフェイズにデッキが空 |
| `turnLimit` | **ターン上限**（`MAX_TURNS = 60`）に到達。ライフの多いほうが勝ち、同値なら引き分け |

**同時に0になったら引き分け。**

`turnLimit` は**終局保証のための安全弁**であり、通常の対戦で到達してはならない
（CLAUDE.md 5章「1万回の自動対戦がすべて規定ターン以内に終了する」）。
デッキ20枚・初期手札4枚・毎ターン1ドローなので、**16ターン前後でデッキが尽きる**。
`turnLimit` 到達率が 0% でないなら、それは設計の失敗として報告する。

## 4. 状態の型定義

`core` は純粋関数のみ（CLAUDE.md 3章）。すべて `readonly`。

```ts
export type PlayerId = 0 | 1
export type CardId = string
export type InstanceId = number

export type Phase = 'setup' | 'draw' | 'main' | 'battle' | 'end' | 'over'
export type Position = 'attack' | 'defense'
export type EndReason = 'lifePoints' | 'deckOut' | 'turnLimit'

export const LIFE_POINTS = 4000
export const DECK_SIZE = 20
export const MAX_SAME_NAME = 2
export const MONSTER_ZONES = 3
export const SPELL_ZONES = 3
export const HAND_SIZE_AT_START = 4
export const HAND_LIMIT = 6
export const MAX_TURNS = 60

export interface MonsterOnField {
  readonly instanceId: InstanceId
  readonly cardId: CardId
  readonly position: Position
  readonly faceDown: boolean
  /** このターンに攻撃したか */
  readonly hasAttacked: boolean
  /** このターンに召喚されたか（表示形式の変更を禁じるため） */
  readonly summonedThisTurn: boolean
  /** このターンに表示形式を変えたか */
  readonly changedThisTurn: boolean
  /** 効果による攻撃力の増減。ターン終了で 0 に戻る */
  readonly atkDelta: number
}

export interface SpellOnField {
  readonly instanceId: InstanceId
  readonly cardId: CardId
  /**
   * 'set'    伏せてある（裏側）
   * 'active' 発動済みで場に残っている（永続・装備・フィールド。**v1 では発生しない**）
   */
  readonly state: 'set' | 'active'
  /** 伏せたターン。同一ターンの発動を禁じるため */
  readonly setTurn: number
  /** 装備魔法だけ使う。装備先のモンスター（v1 では常に null） */
  readonly equippedTo: InstanceId | null
}

export interface PlayerSide {
  readonly lp: number
  readonly deck: readonly CardId[]
  readonly hand: readonly CardId[]
  readonly graveyard: readonly CardId[]
  /** 長さ MONSTER_ZONES。空きは null */
  readonly monsters: readonly (MonsterOnField | null)[]
  /** 長さ SPELL_ZONES。空きは null */
  readonly spells: readonly (SpellOnField | null)[]
  /** フィールド魔法ゾーン。**v1 では常に null**（6.4） */
  readonly field: SpellOnField | null
  /** このターンに通常召喚を使ったか */
  readonly summonedThisTurn: boolean
}

/** 割り込みの最中だけ存在する。攻撃宣言から戦闘計算までの間 */
export interface PendingAttack {
  readonly attacker: InstanceId
  /** null はダイレクトアタック */
  readonly target: InstanceId | null
  /** 防御側がすでに応答したか。true なら二度目は求めない（チェーン1段） */
  readonly responded: boolean
  /** 罠によって無効化されたか */
  readonly negated: boolean
}

export interface GameState {
  readonly phase: Phase
  readonly turn: number
  /** そのターンの手番 */
  readonly turnPlayer: PlayerId
  /**
   * **いま行動を求められているプレイヤー。**
   * 通常は turnPlayer と同じ。割り込み中だけ相手になる。
   */
  readonly priority: PlayerId
  readonly players: readonly [PlayerSide, PlayerSide]
  readonly pendingAttack: PendingAttack | null
  readonly rng: Rng
  readonly log: readonly LogEntry[]
  readonly winner: PlayerId | null
  readonly endReason: EndReason | null
  readonly nextInstanceId: InstanceId
}
```

### 設計上の約束

- **`priority` を `turnPlayer` と分ける。** これが割り込みを `reduce(state, action)` の形の
  まま作れる鍵である。割り込み中は `priority` が防御側を指し、`legalActions(state)` は
  防御側の選べる行動（罠を開く / 流す）だけを返す
- `pendingAttack` は攻撃宣言から戦闘計算までの**一時的な状態**。`null` でないときは
  必ず `phase === 'battle'`
- 乱数は `rng` として持ち回る。`Math.random()` は使わない
- `atkDelta` はターン終了時に 0 へ戻す。永続の増減は v1 では作らない
- **攻撃力・守備力は毎回計算する。カードの値を直接読まない。**
  `rules.ts` の `effectiveAtk(state, ref)` / `effectiveDef(state, ref)` だけを使う。
  v1 では `カードの値 + atkDelta` を返すだけだが、**永続魔法・装備魔法を足す日に
  ここ1か所を直せば済むようにしておく**（6.4）。直接読む場所が10か所あると、
  その日に10か所を探すことになる

## 5. Action 一覧

```ts
export type Action =
  | { readonly type: 'start'; readonly seed: number
      readonly decks: readonly [Deck, Deck]; readonly firstPlayer: PlayerId }
  | { readonly type: 'draw' }
  | { readonly type: 'normalSummon'; readonly handIndex: number
      readonly zone: number; readonly position: Position
      readonly tributes: readonly InstanceId[] }
  | { readonly type: 'setMonster'; readonly handIndex: number
      readonly zone: number; readonly tributes: readonly InstanceId[] }
  | { readonly type: 'changePosition'; readonly instanceId: InstanceId }
  | { readonly type: 'activateSpell'; readonly handIndex: number
      readonly target: InstanceId | null }
  | { readonly type: 'setSpell'; readonly handIndex: number; readonly zone: number }
  | { readonly type: 'toBattle' }
  | { readonly type: 'declareAttack'
      readonly attacker: InstanceId; readonly target: InstanceId | null }
  | { readonly type: 'activateTrap'; readonly zone: number }
  | { readonly type: 'passResponse' }
  | { readonly type: 'endTurn' }
  | { readonly type: 'discardToLimit'; readonly handIndex: number }
```

### 割り込みの流れ

```
[攻撃側] declareAttack
  → pendingAttack が立ち、priority が防御側へ移る
[防御側] activateTrap  または  passResponse
  → 罠を解決（攻撃を無効化する罠なら negated = true）
  → responded = true、priority が攻撃側へ戻る
  → 戦闘計算を行い、pendingAttack を null にする
```

**防御側に伏せカードが1枚も無いときは `priority` を移さず、そのまま戦闘計算へ進む。**
無意味な選択を求めないためで、CPU の手数も減る。

### 補助関数（core、純粋）

```ts
export function legalActions(state: GameState): readonly Action[]
export function isOver(state: GameState): boolean
export function canAttack(state: GameState, m: MonsterOnField): boolean
export function tributesRequired(level: number): 0 | 1 | 2
/**
 * ダメージの受け手は**プレイヤー番号ではなく「攻撃側 / 防御側」**で返す。
 * この関数は数値しか受け取らないので、どちらのプレイヤーかを知らないため。
 * （初版では PlayerId と書いていたが、純粋な計算関数にできないので改めた）
 */
export function battleResult(
  attackerAtk: number, defenderAtk: number, defenderDef: number, position: Position,
): { readonly destroyed: 'attacker' | 'defender' | 'both' | 'none'
     readonly damageTo: 'attacker' | 'defender' | null; readonly damage: number }

/**
 * **攻撃力・守備力はここだけで出す。カードの値を直接読まない**（6.4）。
 * v1 は「カードの値 + atkDelta」を返すだけ。永続魔法・装備魔法を足す日に、
 * 場の 'active' なカードの Continuous を走査して合算する処理をここに入れる。
 */
export function effectiveAtk(state: GameState, ref: InstanceId): number
export function effectiveDef(state: GameState, ref: InstanceId): number
```

## 6. カードデータのスキーマ

**カードIDは `maniwa-tcg` と共通。** 名前・ルビ・説明文・系統・レアリティ・イラストは
そのまま持ち込み、**数値と効果だけを書き直す**。

```ts
export interface MonsterDef {
  readonly id: CardId          // f001 など。maniwa-tcg と同じ
  readonly name: string
  readonly ruby?: string
  readonly kind: 'monster'
  readonly flavor: string
  readonly origin: Origin      // maniwa-tcg と同じ8系統
  readonly rarity: Rarity
  readonly attribute: Attribute // 属性。maniwa-tcg の EnergyType と同じ9種
  readonly level: number        // 1〜8
  readonly atk: number
  readonly def: number
}

/** 魔法の種類（6.4）。v1 が実装するのは 'normal' のみ */
export type SpellType = 'normal' | 'continuous' | 'equip' | 'field' | 'quick'
/** 罠の種類（6.4）。v1 が実装するのは 'normal' のみ */
export type TrapType = 'normal' | 'continuous' | 'counter'

export interface SpellDef {
  readonly id: CardId          // i001（神具）/ u001（絶技）
  readonly name: string
  readonly ruby?: string
  readonly kind: 'spell'
  readonly spellType: SpellType
  /** 出自。神具か絶技か（6.3） */
  readonly form: 'artifact' | 'art'
  readonly flavor: string
  readonly origin: Origin
  readonly rarity: Rarity
  /**
   * **絶技だけが持つ発動条件。** このカードIDの姫神が
   * 自分のモンスターゾーンに表側で存在するときだけ発動できる（6.3）。
   * maniwa-tcg の UltimateCard.requires をそのまま引き継ぐ。
   */
  readonly requires?: CardId
  /** 発動したとき1回だけ起きること */
  readonly onActivate: readonly OneShot[]
  /** 場にある間ずっと効いていること（永続・装備・フィールドのみ） */
  readonly whileOnField?: readonly Continuous[]
}

export interface TrapDef {
  readonly id: CardId          // a001 など
  readonly name: string
  readonly ruby?: string
  readonly kind: 'trap'        // 道標
  readonly trapType: TrapType
  readonly flavor: string
  readonly origin: Origin
  readonly rarity: Rarity
  readonly onActivate: readonly OneShot[]
  readonly whileOnField?: readonly Continuous[]
}
```

**属性は戦闘に影響しない。** `maniwa-tcg` の弱点表は持ち込まない（遊戯王の属性は
戦闘計算に関与しないため）。デッキの色分けと見た目にだけ使う。

### 6.1 姫神の数値の決め方（出発点）

87体を手で決めるのは無理なので、`maniwa-tcg` の値から機械的に出した**たたき台**から始め、
シミュレーションで詰める。**この式は仮であり、測ってから確定する。**

| 新しい値 | たたき台の式 |
|---|---|
| 攻撃力 | **最強ワザの威力 × 20**（10刻みに丸める） |
| 守備力 | **HP × 10**（10刻みに丸める） |
| レベル | **レアリティから**（下表） |

| レアリティ | レベル | リリース |
|---|---|---|
| コモン | 3 | 不要 |
| レア | 4 | 不要 |
| スーパーレア | 5〜6 | 1体 |
| ウルトラレア | 7〜8 | 2体 |

**レアリティがそのままリリース数になる。** `maniwa-tcg` で積み上げたレアリティ判定
（`tools/rarity.ts` の区切り 300 / 255 / 225）の仕事が、そのまま召喚コストとして
生きるということである。

たたき台での実例:

| ID | 名前 | 旧HP | 旧最強威力 | → 攻撃力 | 守備力 | レベル |
|---|---|---|---|---|---|---|
| f002 | カグツチEX | 170 | 105 | **2100** | 1700 | 7 |
| l009 | ダイワスカーレット | — | 120 | **2400** | — | 8 |
| （コモンの例） | — | 60 | 30 | **600** | 600 | 3 |

ライフ4000に対して上位が2100前後なので、**2〜3回殴れば決着**する。
デッキ切れの16ターンより早く終わるはずで、ここは 12章で測る。

### 6.2 神具・絶技・道標の効果は書き直す

`maniwa-tcg` の効果12種のうち `gainEnergy` / `attachEnergy` / `discardEnergy` は
**エネルギーが無いので意味を失う**。`damage` も「モンスターへのダメージ」から
「ライフへのダメージ」に意味が変わる。絶技の `cost`（エネルギー3つ）も同様に消える。

**70種すべての `effects` を書き直す**（神具26 / 絶技18 / 道標26）。
名前・ルビ・説明文・系統・レアリティ・イラストは変えない。
絶技の `requires` だけは**そのまま引き継ぐ**（6.3）。

### 6.3 種別の対応は、カードの性格から決める

`maniwa-tcg` の4種別を、**カードが何であるかに従って**割り当てる。

| maniwa-tcg | 種類数 | このゲーム | なぜ |
|---|---|---|---|
| 姫神 | 87 | **モンスター** | そのまま |
| **神具** | 26 | **魔法** | 九鼎・グングニル・八尺瓊勾玉・黄金の林檎…。**すべて「物」**である |
| **絶技** | 18 | **魔法** | 天叢焼・大地震・九歩の雷・血より生る神…。**すべて「技」**であり、放つ一回きりの出来事 |
| **道標** | 26 | **罠** | 天啓・交代の号令・運命の三女神・ギャラルホルン…。**すべて「兆し」や「合図」**で、状況を引っくり返す側にある |

**魔法44 / 罠26 / モンスター87 = 157枚。イラストが1枚も余らない。**

#### 絶技の発動条件は、そのまま持ち込める

`maniwa-tcg` の `UltimateCard` は最初から条件を持っている。

```ts
/** この絶技を撃てるキャラのカードID。バトル場にいることが条件 */
readonly requires: CardId
```

これは遊戯王の「**自分フィールドに《X》が存在する場合に発動できる**」と同じ形である。
**変換ではなく読み替えで済む。**

しかも**条件は緩くなる**。`maniwa-tcg` では「**バトル場**にいること」＝1枠だったが、
このゲームのモンスターゾーンは**3枠**あるので、同じカードが条件を満たしやすい。

> `decks.ts` より: 絶技は対応するキャラが同じデッキにいないと死に札になるため、
> その属性の絶技を2枚積む

**この死に札問題が3分の1の重さになる。** 2枚積む必要も薄れる。

#### 絶技をスキルに充てる案は取り下げる

前の版では「絶技18種を v2 のスキルに充てる」と書いたが、**取り下げる**。

| | スキルに充てる（旧案） | 魔法にする（新案） |
|---|---|---|
| 使える絶技 | **8種**（1デッキ1つ） | **18種すべて** |
| 実装 | v2。新しい仕組みが要る | **v1。仕組みは何も要らない** |
| 死に札 | 起きない | 起きうるが3枠ぶん軽い |

**新案が全面的に上である。** スキルは v2 で、絶技とは無関係に設計する。

#### v2 で魔法を分けるときの線

v1 の魔法はすべて通常魔法（発動して即墓地）にする。v2 で装備魔法・永続魔法を足すときは、
**`form` がそのまま線になる**。

- `form: 'artifact'`（神具）→ **装備魔法・永続魔法**。物なので場に残るのが自然
- `form: 'art'`（絶技）→ **通常魔法**。技は放てば終わる

**種別を性格から決めておくと、あとの拡張も性格が決める。**

### 6.4 魔法・罠の種類は3層に分かれる

遊戯王の魔法5種・罠3種は、**engine に何を要求するかで3つの層**に分かれる。
v1 は第1層だけを実装するが、**型と `effectiveAtk` は最初から3層ぶん用意する。**

| 層 | 種類 | 要る仕組み | v1 |
|---|---|---|---|
| **第1層** | **通常魔法 / 通常罠** | 何も要らない。発動 → 解決 → 墓地 | **実装する** |
| **第2層** | **永続魔法 / 装備魔法 / フィールド魔法 / 永続罠** | **継続効果の層**（下記） | 型だけ用意 |
| **第3層** | **速攻魔法 / カウンター罠** | **スペルスピード付きのチェーン**（11章） | 型だけ用意 |

#### 第2層が要求するもの ＝ 「攻撃力を保存せず、計算する」

永続魔法「自分のモンスターの攻撃力を500上げる」が場にある間、**攻撃力はカードに
書かれた値ではなくなる**。必要なのは次の4つ。

1. 魔法罠ゾーンのカードが `state: 'active'` で**表側のまま残れる**こと
2. **フィールド魔法ゾーン**（`PlayerSide.field`）
3. **装備先へのリンク**（`equippedTo`）と、装備先が破壊されたときの後始末
4. **攻撃力・守備力を計算で出すこと** — `effectiveAtk(state, ref)`

**4 が本体である。** そして**あとから足すのが一番高くつく。**
v1 で `def.atk` を10か所で直接読んでしまうと、永続魔法を足す日に10か所を探すことになる。

だから **v1 は通常魔法しか出さないが、`effectiveAtk` は最初から通す。**
v1 の実装は `カードの値 + atkDelta` を返すだけの3行でよい。

#### 第3層が要求するもの ＝ スペルスピード

- **速攻魔法**は、伏せておいて**相手のターンにも発動できる**（スペルスピード2）
- **カウンター罠**は、**他の発動に対してだけ**チェーンできる（スペルスピード3）

**カウンター罠はチェーンが無いと意味を持たない。** 無効にする相手の発動が存在しないため。
速攻魔法も「相手のターンに使える」ことが定義なので、第3層が要る。

v1 の割り込みは「相手のバトルフェイズ・攻撃宣言時の1段だけ」（11章）なので、
**この2種類は v1 では作れない。** 型に名前だけ用意しておく。

#### 効果は「1回きり」と「ずっと」に分ける

CLAUDE.md 4章に従って効果はデータで書く。**第2層を足せる形にするため、
最初から2種類に分ける。**

| | いつ効くか | 例 |
|---|---|---|
| `onActivate` | 発動したとき**1回** | ライフを削る / モンスターを破壊する / 引く |
| `whileOnField` | 場にある間**ずっと** | 攻撃力+500 / 攻撃できない / 戦闘ダメージを受けない |

v1 のカードは `onActivate` しか持たない。`whileOnField` は型だけ存在する。

#### 手元の70種を、種類に当てはめた案

**提案であり、実装は v1 の範囲（通常魔法・通常罠）から始める。**

| 種類 | 層 | 当てはまりそうなカード |
|---|---|---|
| **通常魔法** | 1 | **絶技18種すべて**（技は放てば終わる）＋ 消える神具（i001 神饌の香 / i002 供物の果実 / i006 不死の霊薬 / i019 アグニの火箭 / i026 黄金の林檎） |
| **通常罠** | 1 | **道標の大半**（a003 交代の号令 / a006 祟りの札 / a008 焦土の誓い / a019 金翅鳥の急襲 / a023 ギャラルホルン …） |
| **装備魔法** | 2 | i021 グングニル / i023 八尺瓊勾玉 / i024 天の牡牛の角 / i009 生贄の刃 / i005 護符の紐 / i016 銀の鍵。**i007 呪詛の釘は相手のモンスターに装備する弱体化**として使える |
| **永続魔法** | 2 | i025 九鼎（王朝が定まった証しとして**在り続ける**もの）/ i008 星辰の羅針 / i010 双面の鏡 / i012 豊穣の壺 / i022 パンドラの匣 |
| **永続罠** | 2 | a007 封印の陣（**陣は張られたまま**）/ a013 運命の三女神（糸を紡ぎ続ける）/ a020 セルケトの針 / a021 星辰の囁き |
| **速攻魔法** | 3 | u009 光芒一閃（**一閃**なので割り込みそのもの）/ i015 亀甲の卜 |
| **カウンター罠** | 3 | **a026 ヘカの言葉**（言葉で術を解くもの。カウンター罠そのもの）/ a012 神罰 |
| **フィールド魔法** | 2 | **手持ちにほとんど無い。** 場所を表すカードは a016 イシュタルの門 と a018 七つの門 の2枚だけで、どちらも道標（罠）側にある |

#### フィールド魔法は、カードが足りない

**これは正直に書いておく。** フィールド魔法は「場所」を表すカードだが、
神具26種はすべて「物」、絶技18種はすべて「技」なので、**1枚も該当しない**。
道標の a016 イシュタルの門 / a018 七つの門 だけが場所だが、この2枚を罠から
移すと「道標＝兆し」という 6.3 の対応が崩れる。

選べるのは次の3つ。**v2 で決める。**

1. **フィールド魔法を作らない**（v1・v2 とも。一番素直）
2. **新しくカードを足す**（高天原・アスガルド・ルルイエ など、場所の札を作る）
3. **門の2枚を魔法へ移す**（6.3 の対応に例外を作る）

**1 を勧める。** 種類を埋めることが目的ではないし、カードが無いところに
無理に作ると 6.3 の「性格から決める」という筋が崩れる。

## 7. 効果（Effect）の一覧

CLAUDE.md 4章に従い、効果は**データで表現**する。解釈は `core/effects.ts` に一元化し、
カードを足すときにロジックを触らない。

```ts
export type EffectTarget =
  | 'opponent'            // 相手プレイヤー
  | 'self'                // 自分プレイヤー
  | 'opponentMonsterAll'  // 相手モンスター全部
  | 'opponentMonsterOne'  // 相手モンスター1体（発動時に選ぶ）
  | 'ownMonsterAll'
  | 'ownMonsterOne'
  | 'attacker'            // 罠専用。攻撃してきたモンスター

/** 発動したとき1回だけ起きること。**v1 が実装するのはこちらだけ** */
export type OneShot =
  | { type: 'lifeDamage';   target: 'opponent' | 'self'; value: number }
  | { type: 'lifeHeal';     target: 'opponent' | 'self'; value: number }
  | { type: 'destroy';      target: EffectTarget }
  | { type: 'atkChange';    target: EffectTarget; value: number }  // 負値で弱体化。ターン終了で戻る
  | { type: 'draw';         value: number }
  | { type: 'discard';      target: 'opponent' | 'self'; value: number }
  | { type: 'search';       kind: 'monster' | 'spell' | 'trap' }
  | { type: 'negateAttack' }        // 罠専用
  | { type: 'position';     target: EffectTarget; position: Position }
  | { type: 'revive' }              // 自分の墓地のモンスター1体を特殊召喚

/**
 * 場にある間ずっと効いていること（6.4 第2層）。
 * **v1 では型だけ存在し、これを持つカードを作らない。**
 * effectiveAtk / effectiveDef が場の 'active' なカードを走査して合算する。
 */
export type Scope =
  | 'ownMonsters'
  | 'opponentMonsters'
  | 'allMonsters'
  | 'equippedMonster'     // 装備魔法。equippedTo の1体だけ

export type Continuous =
  | { type: 'atkBoost';        scope: Scope; value: number }
  | { type: 'defBoost';        scope: Scope; value: number }
  | { type: 'cannotAttack';    scope: Scope }
  | { type: 'noBattleDamage';  scope: Scope }
  /** 属性やレベルで絞りたいとき。省略なら全部 */
  // filter?: { attribute?: Attribute; minLevel?: number }
```

**`negateAttack` と `attacker` は罠でしか使えない。** `core/effects.ts` が
`pendingAttack === null` のときに拒否する。データ側に書いてしまえる形にはしない。

**`Continuous` は v1 では1枚も使わない。** それでも型を置くのは、
`effectiveAtk` がこれを走査する形で最初から書かれていれば、
第2層を足す日に `core` の他の場所を触らずに済むためである（6.4）。

v1 で新しい効果タイプを足すときは、**先にこの表に追記してから**実装する。

#### 奥行きは付けない（2026-09-25 決定）

実物は盤を寝かせて奥行きを出しているが、**このゲームでは付けない。**

一度 `rotateX` で相手側を奥へ縮める形を作ったが、次の2つが引っかかった。

1. **縮めると 44px の下限を割る。** 実機サイズで測ると相手の魔法罠枠が **43px** になった
   （`rotateX(16deg) scale(0.9)` で縮み率 0.865）。角度を緩めれば満たせるが、
   **見た目の都合で下限に張り付く形になる**
2. **奥行きを出すほど文字が読みにくくなる。** 実物はタップでカードを拡大できるので
   成立しているが、そこまで作らないなら読みやすさを取るほうがよい

**真上から見下ろす形にすると、両方とも起きない。** 両者の場が同じ大きさになり、
カード名も攻守の数字もどこでも同じように読める。卓の面を1枚の板として描き、
中央線で自陣と敵陣を分ける。

#### 立ち絵はデッキの主の姫神

デッキの1枚目の姫神を、その決闘者の顔として隅に置く。
**ライフで絵が切り替わる**（9.3 と同じ規則）ので、盤のカードが1枚も無いときでも
劣勢が伝わる。

#### 隅の札束

| 位置 | 中身 |
|---|---|
| 相手の列の左 | 相手のデッキ（上）と墓地（下） |
| 自分の列の左 | 自分の墓地 |
| 自分の列の右 | 自分のデッキ |

遊戯王の盤は自分から見て**デッキが右・墓地が左**なので、それに合わせる。
札束は枠より小さく（44px 角）置き、モンスターの枠を狭めない。

罠を開けるのは**相手のバトルフェイズ中の1回だけ**である。

### 8.4 対戦相手を選ぶ

> 2026-09-28 追記。

**姫神87体のうち、どれでも対戦相手に指名できる。**
選ばれた姫神が相手の「主」になり、立ち絵（8.1）に出る。

#### 相手のデッキは、その場で組み立てる

主の属性から**決定論的に**20枚を組む。`src/data/autodeck.ts` に置く純粋関数で、
**乱数を使わない**（同じ主なら毎回同じデッキになる）。

```
buildDeck(leaderId) → Deck
```

手順は次のとおり。**core には置かない。** デッキの組み方はルールではなくデータの都合で、
`reduce` の外で決まるためである。

1. **姫神11枚。** 主を必ず入れ、同属性の姫神をレベルの高い順に足す。
   属性の姫神が11体に満たないときは、**レベルの高いほうから2枚目を入れる**
   （同名2枚まで・SPEC 3.1）。それでも足りなければ無属性から補う
2. **魔法5枚。** まず**絶技**のうち `requires` の姫神がこのデッキに居るものを、
   レベルの高い順に最大3枚。残りを**神具**から埋める
3. **罠4枚。** 道標からレベル…ではなくレアリティの高い順に4枚

**`requires` を満たさない絶技は入れない。** 死に札になるため（SPEC 6.3）。

#### いまのカードプールでは、主が違ってもデッキは似る

**魔法は16種、罠は8種しかない**（待ち行列5で44種・18種まで増える）。
**姫神11枚は属性で完全に変わるが、魔法・罠9枚はどの主でもほぼ同じになる。**
これは現状の正直な姿であり、**隠さずに画面にも出す**（「魔法・罠はプール共通」）。

#### 選び方

- **属性で絞り込む。** 9属性のタブ。既定は前回選んだ主の属性
- 主の札を押すと、その主で対戦に進む
- **「おまかせ」を1つ置く。** 押すと87体から1体を選ぶ。**ここだけは乱数を使う**が、
  `Math.random()` は画面側（`src/game/`）でのみ使い、core には持ち込まない

### 8.5 デッキ編集

> 2026-09-28 追記。

**プール111枚から20枚を自由に組める。** あわせて、プリセット（ほのお / みず）や
自作デッキを**複製して直す**こともできる。

| 決めたこと | 中身 |
|---|---|
| 検証 | **`core/actions.ts` の `validateDeck` をそのまま使う**（20枚ちょうど・同名2枚まで） |
| 保存 | 自作デッキは**名前付きで何個でも**。セーブデータに入れる（10章） |
| 消す | 自作デッキは消せる。**プリセットは消せない・直接編集もできない**（複製してから直す） |
| 未完成 | 20枚に満たなくても**保存できる**。ただし**対戦には出せない**。何が足りないかを出す |

**検証を画面側に書き直さない。** 同じ規則を2か所に書くと必ずずれる
（maniwa-tcg 9.1.3 の教訓）。`validateDeck` が返した文言をそのまま出す。

**内訳をその場で出す。** 姫神 / 魔法 / 罠 の枚数と、**`requires` を満たしていない絶技**を
警告として出す。これは検証を落とす条件ではない（入れる自由は残す）が、
死に札だと気付けるようにする。

### 8.6 カードの長押しで詳細を出す

> 2026-09-28 追記。

**対戦中でも、盤と手札のカードを長押しすると詳細が出る。**
対戦画面は札が小さく（手札は最小 44×61px）、名前と攻守しか読めないため。

| 決めたこと | 中身 |
|---|---|
| 出し方 | **長押し 400ms**。指を離す前に出す |
| 押し分け | **長押しの間に動いたら出さない**（スクロールと区別する。閾値 10px） |
| 出したあと | 長押しで開いた詳細を閉じるまで、**その指の離し方では手が進まない**（誤操作で札を出さない） |
| 出すもの | 大きい絵 / 名前とルビ / 種類とレアリティと系統 / 攻守とレベル / 効果の説明 / フレーバー |
| 伏せカード | **相手の伏せカードは詳細を出さない。** 中身が見えてしまうため |
| 閉じ方 | 画面のどこを押しても閉じる。背景も押せる |

**マウスでも動くようにする。** `pointerdown` / `pointerup` / `pointercancel` で書き、
`touchstart` に限定しない。ただし**ホバーには依存しない**（CLAUDE.md 6章）。

**カード一覧（8.3）では長押しではなく1回押しで開く。** 対戦中は「押す＝出す」が
先にあるので長押しにしているが、一覧には他の意味が無いため。

### 9.3 ダメージイラストは**ライフポイント**で切り替える

`maniwa-tcg` では姫神の残りHPで絵が差し替わっていた（無傷 / 傷 / 追い詰められた姿）。
**このゲームにはモンスターのHPが無いので、代わりに持ち主のライフで切り替える。**

| ライフ | 絵 |
|---|---|
| **満タン（4000）** | `<id>.webp`（無傷） |
| **減っている（1601〜3999）** | `<id>-d1.webp`（傷） |
| **1600 以下** | `<id>-d2.webp`（追い詰められた姿） |

**この値は 1万戦で測って決めた**（2026-09-25）。初版では 2667 / 1334 の3等分に
していたが、実測するとライフは終盤まで高いままで、**無傷の絵が 73.6% の時間
出ずっぱりになっていた**。

盤にいる時間をちょうど3等分するのは `d1 ≤ 4000 / d2 ≤ 2800` だった。
つまり「**少しでも減ったら 傷**」は測定のうえでも正しい。

**ただし d2 は 2800（7割）ではなく 1600（4割）にした。** 2800 で
「追い詰められた姿」を出すと言葉の意味が壊れるからである。
3等分は目的ではなく、無傷の絵が出ずっぱりにならないことが目的だった。

| 規則 | 無傷 | 傷 | 追い詰められた |
|---|---|---|---|
| 初版（2667 / 1334） | **73.6%** | 18.3% | 8.1% |
| 3等分（4000 / 2800） | 36.1% | 33%前後 | 33%前後 |
| **採用（4000 / 1600）** | **36.1%** | **50.0%** | **13.9%** |

値は `core/types.ts` の `ART_D2` に置く。**ルールには一切関与しない、表示だけの値である。**

#### なぜこれで筋が通るか

`maniwa-tcg` の `src/data/art/README.md` にこう書かれている。

> 姫神の3枚（**無傷 / 傷 / 追い詰められた姿**）は従来どおり同一衣装で揃える。

**d2 は「追い詰められた姿」であって「瀕死の姿」ではない。** 追い詰められているかどうかは
モンスター1体の話ではなく、その決闘者が置かれた状況の話である。ライフはまさにそれなので、
絵の意図と読み替え先がずれていない。

これにより**150枚のダメージ絵が行き場を失わずに済む**。

#### 決めごと

- **場のモンスターだけ**切り替える。**手札は常に無傷の絵**。まだ出していないカードが
  傷んでいるのはおかしいため
- 相手側も同じ規則で切り替える。**相手の盤を見て自分が勝っているか分かる**
- **自分のモンスターが一斉に切り替わる。** 3体並んでいれば3枚同時に変わる
- **v1 では差し替えだけを入れ、アニメーションを足さない。** `maniwa-tcg` で
  `card--hit` と `card--drained` の取り合いを2度踏んでいる（SPEC 9.4.13）。
  演出は差し替えが安定してから別途
- ライフは1回の戦闘で増減しうる。**絵の判定は戦闘計算が終わってから1回だけ行う**
  （途中の値でちらつかせない）
- 絵の選択は**表示側でライフから決める**。`core` には何も足さない。
  `maniwa-tcg` の SPEC 9.4.11（弱点の演出を描画側で `WEAKNESS_CHART` から引き直した）
  と同じやり方で、決定論リプレイのハッシュを動かさない

#### 失われるもの（正直に）

`maniwa-tcg` では絵が「この姫神があとどれくらい耐えるか」という**他では読めない情報**を
持っていた。ライフに紐づけると、絵は画面に大きく出ている数字と同じことを言うだけになり、
情報ではなく雰囲気になる。

ただし遊戯王型のルールには**モンスターの傷という情報がそもそも無い**ので、
比べる相手は「今の絵」ではなく「何も無い」である。

## 10. セーブデータ

`localStorage`、キーは **`maniwa-duel_v2`**（CLAUDE.md 6章）。
`maniwa-tcg_v1` とは独立。スキーマ変更時はバージョンを上げ、旧データの移行を書く。

### 10.1 v1 → v2 の移行（2026-09-28）

デッキ編集（8.5）と対戦相手の選択（8.4）を足したので、スキーマを上げた。

| 版 | キー | 加えたもの |
|---|---|---|
| v1 | `maniwa-duel_v1` | `deckName` / `record` / `muted` |

## 11. 割り込みを1段に限る理由

> **この章は 11.1 に置き換わった（2026-10-08）。** 人の承認を得てチェーンを入れたので、
> 「1段に限る」はもう実装と合っていない。**章そのものは消さずに残す。**
> 1段に限っていた当時の理由と、そのときの割り切りの形が読めるようにしておくため。
> **いま読むべきは 11.1 である。**


遊戯王が遊戯王である理由は、伏せた罠と、それに割り込む優先権のやりとり
（チェーン・スペルスピード）である。**v1 はここを1段に限る。**

| | v1 | 本家 |
|---|---|---|
| 割り込める場面 | **相手のバトルフェイズ・攻撃宣言時のみ** | ほぼすべての場面 |
| チェーンの深さ | **1段**（罠に罠を重ねられない） | 無制限 |
| スペルスピード | 持たない | 1 / 2 / 3 |
| 解決順 | 罠 → 戦闘計算 | 逆順（LIFO）の解決スタック |

**この割り切りが成立するのは、メインフェイズ2が無いからである。**
罠はバトル前に置ききるしかなく、割り込みが起きうる場所がバトルフェイズに集中する。
**窓口が1か所に絞れるので、解決スタックを持たずに `reduce(state, action)` のまま書ける。**

v2 でチェーンを深くするときは、`pendingAttack` を解決スタックに置き換える。
**そのとき `core` の設計が変わる**ので、v1 のうちにテストを厚くしておく。

**速攻魔法とカウンター罠は、この置き換えが済むまで作れない**（6.4 第3層）。
カウンター罠は「相手の発動を無効にする」カードなので、
**無効にする対象そのものがチェーンでしか生まれない**。

## 11.1 チェーン（LIFO の解決スタック）

> **状態: 実装済み**（2026-10-08）。11章の「1段に限る」を置き換えた。
> 範囲は人が選んだ **B＝攻撃宣言時のみ・深さ無制限の LIFO**。
> スペルスピードと速攻魔法・カウンター罠（6.4 第3層）はまだ入れていない。

### 11.1.1 何が変わったか

| | 旧（11章） | **新（この節）** |
|---|---|---|
| 深さ | 1段 | **無制限**（ただし 11.1.5 の自然な上限がある） |
| 解決 | **即時**。罠を開いたらその場で効果を適用 | **積んでから逆順（LIFO）** |
| 積める側 | 攻撃された側だけ | **1段目は攻撃された側。2段目以降は両者が交互に** |
| 窓口 | 相手のバトルフェイズ・攻撃宣言時のみ | **同じ**（ここは広げていない） |

**窓口を広げていないことが、この変更を小さく保っている。** メインフェイズ2が無いので
（11章）、割り込みが起きうる場所は攻撃宣言のままで、ターン構造は変わらない。

### 11.1.2 状態の型

```ts
/** チェーンに積まれた1枚。解決するまで場から外してここに持つ */
export interface ChainLink {
  readonly player: PlayerId
  readonly cardId: CardId
}

export interface PendingAttack {
  readonly attacker: InstanceId
  readonly target: InstanceId | null
  readonly negated: boolean
}
```

`GameState` に2つ足す。

| 項目 | 意味 |
|---|---|
| `chain: readonly ChainLink[]` | 積まれた順。**末尾が最後に積まれた札＝最初に解決する札** |
| `chainPasses: number` | 連続でパスした回数。**2 になったら解決する** |

**`PendingAttack.responded` は廃止した。** 「もう応答したか」という1ビットでは
交互の積み合いを表せないので、`chainPasses` が役目を引き継ぐ。

`turnPlayer` と `priority` を分けてあること（4章）は**そのまま効く**。
チェーンは優先権を往復させるだけなので、この分離が無ければ書けなかった。

### 11.1.3 手順

1. **攻撃宣言**で窓が開く。`chain` は空、`chainPasses` は 0。
   優先権は**攻撃された側**へ移る
2. 優先権を持つ側は **「罠を1枚積む」** か **「パス」** のどちらかを選ぶ
   - 積んだ → `chain` の末尾に足し、`chainPasses` を **0 に戻し**、優先権を相手へ
   - パス → `chainPasses` を 1 増やし、優先権を相手へ
3. **`chainPasses` が 2 になったら**（両者が連続でパスした）チェーンを**逆順に解決**する
4. 解決が終わったら戦闘計算へ進む

**チェーンが空のまま両者がパスしたときは、そのまま戦闘計算へ進む**（旧実装と同じ）。

**伏せカードが1枚も無い側には優先権を渡さない。** 無意味な選択を求めないためで、
これも旧実装から引き継いでいる。チェーンの途中でも同じで、**積める札が無い側は
自動でパスしたものとして扱う。**

### 11.1.4 積める条件

| 条件 | 理由 |
|---|---|
| 通常罠であること | v1 は第1層だけ（6.4） |
| 伏せたターンではないこと | 既存の規則をそのまま引き継ぐ |
| **`chain` が空なら、積めるのは攻撃された側だけ** | 窓を開けるのは防御側という形を保つ |
| **`chain` が空でなければ、両者が積める** | これがチェーンの本体 |

**積んだ時点で伏せゾーンから外す。** 同じ札を二度積めないようにするためで、
カードは `ChainLink` が持ち、**解決したときに墓地へ送る。**

### 11.1.5 深さの上限は自然に決まる

**無制限と書いたが、実際には有限である。** 伏せゾーンは1人3つ（`SPELL_ZONES = 3`）で、
積むたびにゾーンから外れるので、**チェーンは最大6段で必ず止まる。**

**この性質が停止性を保証している。** 無限ループを別途防ぐ仕掛けは要らない。
CLAUDE.md 5章の「終局保証」はこれで守られる。

### 11.1.6 解決は逆順

```
積んだ順:   A（防御側） → B（攻撃側） → C（防御側）
解決の順:   C → B → A
```

各リンクについて、`onActivate` を適用してからカードを墓地へ送る。

**解決の途中で決着したら、そこで止める。** ライフが0になった時点で以降のリンクは
解決しない。**`negateAttack` は解決時に `pendingAttack.negated` を立てる**ので、
チェーンのどこにあっても効く。

**解決の途中で攻撃側の姫神が消えることがある。** 戦闘計算はもともとこれを見て
いるので（`attacker === null` の分岐）、扱いは変わらない。

### 11.1.7 まだやらないこと

- **スペルスピード**。いまは通常罠しかないので、積める札の格付けが要らない
- **速攻魔法・カウンター罠**（6.4 第3層）。カウンター罠は「相手の発動を無効にする」
  ので、**チェーンのリンクを指して無効にする**仕掛けが要る。`negateAttack` は
  攻撃しか指せない。ここは次の段
- **メインフェイズの応答窓**。窓口を増やすとターン構造が変わる

### 11.1.8 画面（8.2 の更新）

チェーンが積まれている間は、**積まれた札を下から順に並べて見せる。**
優先権を持つ側に「重ねる／パス」の2択を出すのは旧実装と同じで、
**違うのは「いま何が積まれているか」が見えることである。**

解決は逆順なので、**上（最後に積んだ札）から順に消えていく**ように見せる。

#### 帯が見えるのは「訊かれているあいだ」だけ（2026-10-08 実測）

**この帯が出るのは、人が応答を求められている最中に限られる。**

`advanceChain` は、応答できる側が尽きた時点で**同じ `reduce` の中で解決まで進める**。
そのため「自分が1枚積んで、相手に積む札が無い」ときは、積んだ姿が画面に残らない。
**人が見るのは、罠の効果とその結果だけである。**

実測（2026-10-08・390×844）。描画そのものは確かめてある。

```
{"label":"チェーン2段","links":["1. 祟りの札","2. 神罰"],
 "帯がある":true,"帯の幅":374,"画面の幅":390,"横スクロール":false}
```

**14試合を自動操作で回したときは、帯が一度も出なかった**（画面で見た最大0段）。
`core` では2段以上が32.6%の試合で起きている（3000戦の実測）ので、
**帯が出る条件が狭いということである。**

「積んだ瞬間を必ず見せる」ようにするには、解決を次の描画まで遅らせる必要がある。
**これは `reduce` の外（画面側）の話なので、`core` を触らずにできる。** 未着手。

## 12. テスト方針

CLAUDE.md 5章の必須3項目は必ず作る。

| テスト | 内容 |
|---|---|
| **決定論リプレイ** | 同一シード＋同一入力列 → 最終状態のハッシュが完全一致 |
| **ルール不変条件** | ライフ・手札枚数・デッキ枚数・ゾーンの数が負値や NaN にならない。ゾーンの長さが常に3 |
| **終局保証** | 1万回の自動対戦がすべて `MAX_TURNS` 以内に終了する |

このゲーム固有で足すもの:

| テスト | 内容 |
|---|---|
| 戦闘計算 | `battleResult` の表（3.6）を全パターン |
| 召喚コスト | レベルとリリース数の対応。リリース不足で召喚できないこと |
| **通常召喚は1ターン1回** | セットも消費すること |
| **伏せたターンに罠を発動できない** | `setTurn === state.turn` で拒否されること |
| **割り込みは1段** | `responded === true` のあと二度目の `priority` 移譲が起きないこと |
| **伏せカードが無いと止まらない** | `declareAttack` から直接戦闘計算へ進むこと |
| 先攻1ターン目 | ドローしない・バトルフェイズに入れない |
| 手札上限 | エンドフェイズに6枚へ落ちること |
| 効果の適用 | `negateAttack` と `attacker` が罠以外で拒否されること |
| `core` 純粋性 | 既存の `tests/core-purity.test.ts` が自動で拾う |

## 13. シミュレーション指標（`npm run sim`）

1万回の自動対戦。CLAUDE.md 5章の必須項目:

- **先手勝率**（45〜55% を逸脱したら要調整）
- 平均ターン数・平均試合時間
- カード別の採用率と勝率寄与
- **一度も使われなかったカードの一覧**

このゲーム固有で出すもの:

| 指標 | 見たいこと |
|---|---|
| 決着理由の内訳（`lifePoints` / `deckOut` / `turnLimit`） | **`turnLimit` は 0% であるべき** |
| **デッキ切れ決着の割合** | 高すぎるなら打点が足りない |
| **ライフの推移**（ターンごとの中央値） | **9.3 の絵の区切りをここから決める** |
| 罠の発動率 | 低すぎるなら割り込みが機能していない |
| ダイレクトアタックの割合 | 高すぎるなら盤面が維持できていない |
| リリース召喚の回数 | 0に近いなら上位モンスターが出せていない |

**数値が基準を外れても、独断でカードデータを書き換えない**（CLAUDE.md 5章）。報告のみ。

## 13.3 姫神の数値の検算（`tools/rarity.ts`）

2026-09-29 追加。

6.1 の式どおりに 87体の数値が出ているかを機械で見る。

```
node games/maniwa-duel/tools/rarity.ts          # 全87体
node games/maniwa-duel/tools/rarity.ts --diff   # ずれだけ（あれば終了コード1）
```

見るのは4つ。

| 検査 | 式 |
|---|---|
| 攻撃力 | 最強ワザの威力 × 20（10刻みに丸め） |
| 守備力 | HP × 10（10刻みに丸め） |

| SR・UR の段 | 総合力が境目以上なら上の段（SR 267 / UR 332） |

**maniwa-tcg のレアリティ判定をやり直す道具ではない。** こちらの取り決めは
「あちらの値から機械的に出す」なので、**出した値が式どおりか**だけを見る。
総合力の式（`HP + 効率×3 + 最大威力×0.6`）は「どちらの段に寄せたか」を
再現するためだけに使う。

**元の値は maniwa-tcg 側にある。** 姫神の HP とワザはあちらが持っているので、
検算にはあちらのカード定義と `expectedDamage` を読む。

**検知することを確かめてから使うこと。** 導入時（2026-09-29）に2通りで実測した。

| 試した壊し方 | 出力 | 終了コード |
|---|---|---|
| `f001` の攻撃力を 1400→1410 | `攻撃力 1410 ≠ 1400（威力 70.0 × 20）` | **1** |
| `f002` のレベルを 8→7（帯の中だが段が違う） | `レベル 7 ≠ 8（総合力 348.0 / 境目 332）` | **1** |
| 何もしない | `ずれているカード: 0 枚` | 0 |

2つ目は**帯の中に収まっているのに間違い**という場合で、帯だけを見ていると
見逃す。段の検査が効いていることの確認になる。

## 13.4 1枚の価値を差し替えで測る（`tools/card-value.ts`）

2026-09-30 追加。

```

```

**「既存の何と比べて強いのか」を出す道具である。** プール全体の平均では比較の相手が
定まらない。同じ種別の1枠を対象カードに差し替え、**抜いた札と入れた札の勝率寄与を並べる**。

```
=== 豊穣の壺（i012）の価値 ===
  2000 戦 / デッキ「ほのお」の アグニの火箭（i019）と差し替え

  抜いた アグニの火箭   採用  29.4%  勝率  61.1%  寄与 +11.1pt
  入れた 豊穣の壺       採用  59.1%  勝率    48%  寄与 -2pt

  差分 -13.1pt（プラスなら アグニの火箭 より強い）
```

**`decks.ts` のファイルは書き換えない。** `sim.ts` に足した `--swap` に渡して、
読み込んだ配列の**写しの上で**差し替える。ファイルを触ると、失敗したときに
差し替えたまま残る危険がある。

### `sim.ts --swap`

```
--swap=<デッキ名>:<抜くID>:<入れるID>
```

差し替えた結果が `validateDeck` を通らなければ終了コード2で止める。
1枚を1枚に替えるので枚数は変わらないが、**同名3枚目**が生まれることはありうる。

### 絶技は対応姫神が同じデッキに要る

`requires` を持つ魔法は、対応する姫神が同じデッキにいないと死に札になる（6.3）。
**差し替え先を選ぶ時点で弾く。** 入れた札が一度も撃てないまま「寄与ほぼ0」と出ると、
弱いのか撃てないのかが区別できないためである。

> **この分岐は、まだ一度も通っていない。** 2026-09-30 時点でプールに載っている
> 絶技6種は、すべて対応姫神がプリセットデッキに入っている。
> **待ち行列5で残り12種を足した時点で到達しうる**ので、そのとき動きを確かめること。

## 13.5 プールデッキ（`--decks=pool`）

2026-10-01 追加。待ち行列の第1段はこれで終わり。

```
npm run sim -- --decks=pool
```

プリセットデッキは2つ固定なので、**そこに入っていないカードは永久に一度も戦わない**。
待ち行列5で魔法・罠を増やす予定なので、固定デッキだけでは足したカードの性能が
永久に分からない。`src/data/pool-decks.ts` が**カードプール全体から20枚を抽選**する。

| 決めたこと | 中身 |
|---|---|
| 内訳 | プリセットと同じ **姫神11 / 魔法5 / 罠4** |
| 抽選 | **一様**。強い順に選ぶと、弱い札は選ばれず→測れず→弱いと分からない循環に入る |
| 乱数 | core の PRNG をシードから回す。`Math.random()` は使わない |
| ラウンド | **36回引き直す**。1つの抽選結果に固定すると、そのデッキの札しか測れない（当初12回。2026-10-09 に増やした。下の「12回では足りなかった」） |
| 属性 | **9属性すべて**。無属性を外すと n001〜n009 の9体が永久に測れなくなる |
| 絶技 | `requires` の姫神がそのデッキに居るものだけを候補にする（6.3） |

**`autodeck.ts` とは別物である。** あちらは対戦相手を組むための決定論的な「強い順」、
こちらは計測のための一様抽選。混ぜない。

### 12回では足りなかった（2026-10-09）

**絶技は9デッキのうち1つでしか候補にならない。** `requires` の姫神と属性が
揃うデッキが1つだけだからである。そのデッキで魔法5枠に入る確率は約19%なので、
12ラウンドだと **0.81^12 ≈ 8% の確率で一度もデッキに入らない。**

139枚のプールで実際にそれが起きた。`u016 血より生る神` は
**デッキ入り0回**で、採用率0%の正体は「AIが出さない」ではなく
**「抽選が一度も配らなかった」**だった。関門 d4 を2夜止めていたのはこれである。

36回に増やすと 0.81^36 ≈ 0.05% まで下がる。**総試合数は変わらない**
（6万戦指定で 12ラウンド×30戦 = 36ラウンド×10戦 = 58320戦）。
ラウンドを増やしても1枚あたりの期待デッキ入り数は変わらず、ばらつきだけが縮む。

**プールがこれ以上増えたら、また足りなくなる。** 絶技の見張り（13.6）が
「標本不足」を出したら、カードではなくここを疑うこと。

### 無属性を外しかけた

最初は「姫神が9体しかなく重複が増えて偏る」として無属性を抽選対象から外していた。
**実測すると n001〜n009 の9体が未使用として並んだ。** 検査が9枚ぶん盲目になるほうが、
重複の偏りよりはるかに悪い。9体から11枚引くと2枚は同名の2枚目になるが、
同名2枚までは規則の範囲内である（3.1）。ほのお10体・やみ10体でも1枚は2枚目になる。

### 「未使用」は**実際に出された**かどうかで数える

`maniwa-tcg` と同じ定義（あちらの `usedIn === 0`）にそろえてある。
デッキに入っただけでは使用と数えない。

> **2026-10-01 時点で、この検査は通っていない。** 6万戦でも4枚が一度も出なかった。
> 内訳と原因は同日の夜間レポートに書いた。**カードデータの問題ではなく、
> `tools/ai.ts` の評価の問題**である。関門 d4 はこれで止まる。
>
> **着手は保留した。** 課題は CLAUDE.md 9章「今後の宿題」に写してある（4枚の内訳・

>
> 既定の1万戦では `u006 星辰再臨` も未使用に落ちるが、6万戦では使われる。
> 関門は6万戦で測るので、**通すべき枚数は4枚**である。
>
> **2026-10-09 追記: 絶技はこの数えかたから外した。** 代わりの数えかたは 13.6。

## 13.6 絶技は採用率で数えない（2026-10-09 決定）

人の判断で入れた変更である。**自分で基準を緩めたのではない。**
2夜連続で関門 d4 が `u016 血より生る神` 1枚で止まり、原因が
「カードの良し悪しではなくプールの希釈」だと2つの物差しで再現したので、
案を出して選んでもらった。

### 何が間違っていたか

絶技は **`requires` の姫神が同じデッキに引けていないと候補にならない**（13.5）。
そのため採用率は、プールに**絶技と無関係なカードを足すだけで下がる**。

| 測った夜 | プールの枚数 | `u016` の採用率 |
|---|---|---|
| 10-05 | 131枚 | 0.4% |
| 10-06 | 135枚 | 0.3% |
| 10-07 | **139枚** | **0%** |
| 10-08（追加前） | 135枚 | 0.3% |
| 10-08（追加後） | **139枚** | **0%** |

同じ夜に135枚で通り139枚で落ちている。**カードを足すほど落ちる検査**になっていた。
待ち行列5はあと22枚足してプールは161枚になる予定なので、このままでは落ち続ける。

### 代わりに何を見るか

**「デッキに入った試合のうち、実際に出せた割合」**を見る。

```
出せた割合 ＝ 出した試合数 ÷ デッキに入った試合数
```

デッキに入った試合数は `sim.ts` の `cardInDeck` が数える（同名2枚でも1と数える）。
**この比はプールの枚数で割られないので、カードを足しても動かない。**
採用率を置き換えた理由はこれだけである。

### 止める条件は緩めていない

| 条件 | 扱い |
|---|---|
| **出した試合数が 0** | **落ち**（従来の「一度も使われなかった」と同じ） |
| デッキ入りが100試合未満 | **落ち**（抽選側の不具合。測れていない） |
| 出せた割合が 5% 未満 | **記録のみ。マージは止めない** |

「一度も出ない」は札が死んでいる証拠なので止める。
いっぽう「出にくい」は強さの話で、**強さの数値は報告のみと決まっている**
（CLAUDE.md 5章）。5% という線は下の実測（最小 0.7%・次が 15.4%）から引いた。
**数字を合わせるために線を動かしてはいけない。**

### 実測（2026-10-09・135枚・プール抽選6万戦）

| ID | 名前 | デッキ入り | 出した | 出せた割合 | 判定 |
|---|---|---|---|---|---|
| u011 | 焼き払う剣 | 2160 | 844 | **39.1%** | OK |
| u016 | 血より生る神 | 1080 | 326 | **30.2%** | OK |
| u019 | 千の御名 | 3240 | 882 | 27.2% | OK |
| u002 | 世界樹の恵み | 2160 | 582 | 26.9% | OK |
| u001 | 天叢焼 | 3240 | 695 | 21.5% | OK |
| u010 | 大地震 | 1080 | 208 | 19.3% | OK |
| u005 | 神威の雷 | 3240 | 499 | 15.4% | OK |
| u006 | 星辰再臨 | 2160 | **16** | **0.7%** | 低率（記録のみ） |

**`u016` は 30.2% である。** 採用率では0%として関門を2夜止めていた札が、
この数えかたでは8種のうち2番目に出せている。希釈が原因だったという読みは、
これで3つめの物差しでも裏が取れた。

### `u006 星辰再臨` だけが低い理由（報告のみ）

`u006` の `requires` は **`w002 クトゥルフEX`（Lv7・攻1800）**である。
Lv7 は生贄2体なので、`score()` は場の打点の合計を見るかぎり
**攻1800を得るために2体ぶんの打点を失う**と計算する。
`w002` は `onSummon` に `discard opponent 1` を持つが、
**相手の手札が1枚減ることは `score()` の見ている打点に表れない。**

同じ Lv7〜8 でも `s001`（攻2000・`lifeHeal` + `draw`）や `t003` は使われている。
効果がライフや自分の手札を動かすので採点に乗るからである。
**これは CLAUDE.md 9章の「打点に表れない投資を評価できない」そのものであり、
`u006` のカードデータの問題ではない。** 書き換えないこと。

### やらないこと

- `tools/ai.ts` の評価関数を直すこと。**この変更は検査の数えかただけを変えた。**
  CLAUDE.md 9章の宿題は閉じていない
- 固定デッキ（`--decks=fixed`）の未使用判定から絶技を外すこと。
  固定デッキは中身が動かないので希釈が起きない。**あちらは従来どおり**

## 13.2 知らない引数は黙って無視しない

2026-09-28 追加。

`npm run sim` は2本のゲームを続けて回し、**同じ `process.argv` を両方に渡す**。
そのため maniwa-tcg 向けの引数がこちらにも届く。

**`--decks=pool` は maniwa-tcg のプール抽選を指すが、maniwa-duel はこれを解釈しない。**
それでも固定デッキのまま完走し、「一度も使われなかったカード: なし」と出す。
**pool の検査をしたつもりで fixed の結果を読むことになる。**

対策は2つ。どちらも「測ったつもり」を防ぐためのものである。

1. **知らない引数は声を出す。** `--games` / `--seed` 以外の `-` で始まる引数を受け取ったら、
   無視した旨を出す。`--decks` のときは、下の未使用一覧が固定デッキの結果であることも添える。
   **終了コードは変えない**（同じ実行に乗っている maniwa-tcg を妨げないため）
2. **未使用一覧の見出しに範囲を書く。** 「固定デッキの N枚が対象。プール全体ではない」。
   対象は `DECKS` に入っているカードの和集合であって、`ALL_CARDS` ではない

```
  ⚠ --decks=pool は maniwa-duel では解釈しません。無視して固定デッキで実行します
     プール抽選は未実装です（SPEC 13.2）。下の「一度も使われなかったカード」は
     **固定デッキの結果**であって、カードプール全体の検査ではありません

■ 一度も使われなかったカード（固定デッキの 39 枚が対象。プール全体ではない）
```

**これは `--decks=pool` の実装ではない。** プール抽選そのものは未実装のままで、
実装するまでの間、読み違えを防ぐだけの措置である。
実装したら `KNOWN_OPTIONS` に `--decks` を足し、この節を書き替えること。

## 13.1 巻き戻し検査（`tools/data-diff.ts`）

2026-09-28 追加。

夜間ジョブが「既存カードの数値を巻き戻していないか」を機械的に確かめるための道具。

```
node games/maniwa-duel/tools/data-diff.ts <基準のref> [比較先のref]
```

`MONSTERS` / `SPELLS` / `TRAPS` の3つを読み、**カードIDごとに内容を JSON 化して
突き合わせる**。比較先を省くと作業ツリーの現在の内容を使う。

- **消えたカード**か**内容が変わったカード**が1件でもあれば**終了コード1**
- **増えただけなら 0**。待ち行列5で魔法・罠を足していくため、増加は正常とみなす

**行数で測らない理由。** `git diff --numstat` の削除行数で判定すると、配列の末尾に
1件足すだけで嘘の警告が出ることがある。maniwa-tcg 側で 2026-09-23 に実際に踏んでいる
（既存153枚が1枚残らず一致していたのに関門が落ちた）。守りたいのは行数ではなく
**データの同一性**なので、測る対象を目的に合わせる。

**検知することを確かめてから使うこと。** 導入時（2026-09-28）は、`f001` の `atk` を
1400→9999 に変えた場合と、`u001` を配列から削除した場合の2通りで、
どちらも終了コード1を返すことを実測している。**「通る」ことだけを確かめた関門は、
壊れていても通るので意味が無い。**

## 18. デッキ編集の画面でも長押しで詳細を出す／レベルの絞り込み

### 18.1 長押しが要る場所

8.6 は「一覧は1回押しで開く。対戦中は『押す＝出す』が先にあるので長押しにする」と

|---|---|

> デッキを組むときに最も見たい軸である。

## 19. 効果を持つ姫神

> 2026-10-02 追記。モチーフ（遊戯王デュエルリンクス）に合わせる要望による。
> **既存の姫神に効果を足すことは、作者が明示的に許可した**（CLAUDE.md 5章の例外）。

### 19.1 v1 が作る発動タイミングは2つだけ

デュエルリンクスの姫神の効果は、発動のきっかけで何種類にも分かれる。
**v1 はそのうち2つだけを作る。**

| タイミング | 作る | 理由 |
|---|---|---|
| **召喚時**（`onSummon`） | **作る** | 1回きりの効果なので、既存の `OneShot` と `effects.ts` がそのまま使える |
| **破壊時**（`onDestroyed`） | **作る** | 同上 |
| 攻撃宣言時 | 作らない | 割り込みが1段という制約（11章）に触れる。罠の `negateAttack` と同時に起きたときの順序を決める必要がある |
| 永続（場にある間ずっと） | 作らない | SPEC 6.4 の**第2層**。`Continuous` と `effectiveAtk` の合算が要る |
| 起動（1ターンに1回使う） | 作らない | 「使う」という操作が増える。`legalActions` と画面の両方に手が要る |

**選ばなかった3つは、v1 のあとの候補に入れる**（15章）。

### 19.2 型

`MonsterDef` に2つの任意項目を足す。**どちらも `OneShot` の配列**で、
魔法・罠とまったく同じものを使う。効果の解釈は `core/effects.ts` の1か所のまま。

```ts
export interface MonsterDef extends CardBase {
  readonly kind: 'monster'
  // …既存の項目…
  /** 表側で召喚に成功したときに1回だけ起きること */
  readonly onSummon?: readonly OneShot[]
  /** 戦闘または効果で破壊されたときに1回だけ起きること */
  readonly onDestroyed?: readonly OneShot[]
}
```

**新しい効果タイプは作らない。** 7章の表にあるものだけで書く。

### 19.3 発動する条件

| | 決めたこと |
|---|---|
| `onSummon` | **表側で召喚に成功したときだけ。** セット（裏側守備表示）では出ない |
| | リリースを使った上級召喚でも出る |
| | 効果の持ち主は**召喚したプレイヤー** |
| `onDestroyed` | **戦闘で破壊された / 効果（`destroy`）で破壊されたときだけ** |
| | **リリース（生贄）では出ない。** リリースは破壊ではない |
| | **デッキ切れや墓地送りでは出ない** |
| | 効果の持ち主は**破壊された姫神を出していたプレイヤー**（破壊した側ではない） |

### 19.4 1体を選ぶ効果は使わない

魔法・罠は発動時に `opponentMonsterOne` / `ownMonsterOne` を選べるが、
**姫神の効果は勝手に発動するので、選ぶ機会が無い。**

したがって姫神の効果には **`needsChoice` が真になる効果を書かない。**
全体（`opponentMonsterAll`）かプレイヤー（`opponent` / `self`）を対象にする。

**この約束はテストで守る**（`tests/monster-effect.test.ts`）。

### 19.5 連鎖の深さは2段まで

破壊時の効果が別の姫神を破壊すると、その姫神の破壊時の効果がまた動く。
**深さ2段で打ち切る。** 3段目は起きない。

無限に続かないことを型や証明で示すのは難しいので、**数で止める。**
11章で割り込みを1段に限ったのと同じ考え方である。

### 19.6 画面での見せ方

| 場所 | 出すもの |
|---|---|
| 詳細（8.6） | **「召喚時」「破壊時」の見出しつきで効果文を出す。** 魔法・罠と同じ書式 |
| 盤・手札の札 | **効果を持つ姫神に印を出す。** 小さい札では効果文は読めないため |
| カード一覧（8.3） | 絞り込みに**「効果持ち」**を足す |

**印は絵を隠さない位置に置く。** 既存のレベル星バッジ・属性バッジを消さない
（art/README.md のとおり、この2つは種別を見分ける唯一の手がかりである）。

### 19.7 レアリティの検算との関係

`tools/rarity.ts` は **攻撃力＝最大威力×20 / 守備力＝HP×10 / レベル＝レアリティ**
で検算している。**効果はこの式に入っていない。**

つまり**効果を足してもレアリティの検算は通る**が、
**同じレベル・同じ攻守でも、効果を持つ姫神のほうが強い。**

v1 では式を変えない。**強さは `tools/card-value.ts` と `--decks=pool` の
勝率寄与で測り、式に取り込むかどうかは実測を見てから決める。**

### 8.7 対戦中の履歴

> **状態: 実装済み**（2026-10-08）。人の指摘「何が起きているか分かりにくい」への直し。

#### なぜ要るか

**`core` はすべての出来事を `state.log` に記録しているのに、対戦画面は一度も出していなかった。**
画面がログを読むのは「直前が拒否だったか」を見る1か所だけで、
**プレイヤーは何が起きたかを知る手段を持っていなかった。**

とくに相手の番は、召喚・魔法の発動・攻撃・チェーンが続けて起き、
**終わったあとに盤面だけが変わっている。** 何をされたのか分からない。

#### 2つに分けて出す

| | 出すもの | どこ |
|---|---|---|
| **直前の1件** | 最後の出来事を1行 | 説明の行（常時） |
| **ぜんぶ** | ターンごとにまとめた全履歴 | 履歴の幕（ボタンで開く） |

**直前の1件は、説明の行に出す。** 相手の番は「相手の番です」としか出ていなかった。
**待っているあいだに何が起きたかを、そこに出すほうが素直である。**
自分が操作を求められているときは、**操作の案内を優先する**（そちらを消さない）。

#### 履歴の幕

- **開き方**: **説明の行の右端に置く「履」ボタン。** 常時出す
  - **文脈で変わるボタン列には置かない**（割り込み中など、出ない場面があるため）
  - **上部（早送りの隣）にも置かない。** そこは「相手のメイン」を大きく出す場所で
    （8.1）、44px のボタンを足すと**帯の幅が 73px に落ちて文字が2行に折れる**
    （2026-10-08 実測）。タップ領域は 44px 未満にできないので、譲るのは上部のほう
  - 縦持ちで親指が届くのは下側なので、置き場所としても下が素直である
- **並び**: 古いものが上、新しいものが下。**開いたときは一番下へ送る**
- **まとめ方**: ターンごとに見出しを付ける
- **誰の行いか**: 行の頭に「自分」「相手」を出す
- **閉じ方**: どこを押しても閉じる（8.6 と同じ）

#### 出さないもの

**`rejected` は出さない。** これは「その操作はできない」という画面と CPU への返事で、
**盤の上で起きた出来事ではない**。混ぜると、起きていないことが起きたように読める。

#### 種別の言葉

`LogEntry.kind` は内部の識別子なので、**画面に出すときは日本語にする**。
対応表は `view.ts` に1つだけ置く。**詳細文（`detail`）は `core` が作ったものをそのまま出す。**

| kind | 画面の言葉 |
|---|---|
| `turn` | ターン |
| `draw` | ドロー |
| `summon` / `set` | 召喚 / セット |
| `spell` / `trap` | 魔法 / 罠 |
| `effect` | 効果 |
| `attack` / `battle` | 攻撃 / 戦闘 |
| `destroy` | 破壊 |
| `damage` / `heal` | ダメージ / 回復 |
| `discard` / `search` / `revive` | 手札を捨てる / サーチ / 蘇生 |
| `respond` / `pass` / `negate` | 応答 / スルー / 無効 |
| `flip` / `position` | 反転 / 表示形式 |
| `phase` / `over` | フェイズ / 決着 |

**表に無い kind は、識別子をそのまま出す。** 黙って消すと、
新しい kind を足したときに履歴から抜けたことに気付けない。

### 9.4 この画面の動きは `transition` では出せない（2026-10-22 実測）

#### 9.4.1 測って分かったこと

`renderDuel` は毎回 `root.textContent = ''` から組み直す。
**札も、`.board` も `.hand` も、描き直しのたびに新しい要素になる。**

実機で確かめた（390×844 / `deviceScaleFactor: 2`）。盤と手札の要素に印を付け、
1手進めてから数え直した結果がこれである。

| | 描き直し前 | 描き直し後 |
|---|---|---|
| 印の付いた手札の札 | 4 | **0**（札そのものは4枚ある） |
| 印の付いた盤の札 | 1 | **0**（札そのものは1枚ある） |
| 印の付いた入れ物（`.board` / `.hand`） | 2 | **0** |

**新しい要素には「変化の前の値」が無いので、CSS の `transition` は原理的に発火しない。**

> **既にある `.hand__slot .card { transition: transform 0.12s ease-out }` は、
> この理由で一度も効いていない。** `.card--selected` の `translateY(-8px)` は
> 毎回いきなり出ている。**この行は消さない**（消すと「なぜ無いのか」が分からなくなる）。
> 動かしたいものは下の形で足す。

#### 9.4.2 だから `animation` ＋ 一度きりのクラスで出す

`animation` は**新しい要素でも最初から再生される**ので、こちらは出る
（`.card--openable` が実際に動いているのはそのため）。

**ただし、状態から直に決まるクラスに `animation` を付けてはいけない。**
`.card--defense` に付けると、守備表示でいる**あいだじゅう毎回**再生される。

**前の描き直しの状態を持ち回り、変わったときだけ一度きりのクラスを足す。**
姫神演義が `prevXxx` で揃えているのと同じ形である（maniwa-tcg SPEC 9.4.12）。

```
描画の直前  : 前回の position を instanceId ごとに引く
変わっていた : card--flip-to-defense / card--flip-to-attack を足す
描画の最後  : 今回の position を控える
```

**盤から消えた姫神は控えから落とす。** 残したままだと、同じ instanceId が
再利用されたときに身に覚えのない回転が出る。

#### 9.4.3 最初の1つ — 表示形式を変えたら、札が回る

遊戯王の盤で**いちばん目に付く動きは、札が横を向くこと**である。
`.card--defense` は `transform: rotate(90deg) scale(0.7)` を当てているので
**向き自体は出ている**が、**切り替わる瞬間が無い**（実測で `transition` は効いていない）。

| クラス | 動き | 終わったあとに残る値 |
|---|---|---|
| `card--flip-to-defense` | `rotate(0) scale(1)` → `rotate(90deg) scale(0.7)` | `.card--defense` の値 |
| `card--flip-to-attack` | `rotate(90deg) scale(0.7)` → 無し | 無し |

**どちらも 0.22 秒。** `.card--defense` の静止値を書き換えないので、
**既存の規則には一行も触らない。**

#### 9.4.4 動きを減らす設定では止める。**代わりは要らない**

`prefers-reduced-motion: reduce` では `animation: none` にする。

**「動かさない代わりに何も出さない」には当たらない。** この動きが伝えているのは
「向きが変わった」ことで、**向きそのものは `.card--defense` の静止した回転で
見えたままだからである。** 姫神演義が踏み込み・入れ替えについて
「位置そのものが動くので、動かさなくても結果は見える」と決めたのと同じ理由
（maniwa-tcg SPEC 9.4.20）。

### 9.5 ライフが動いた瞬間を出す（2026-10-23）

#### 9.5.1 測って分かったこと：**何も出ていない**

`lifeBanner` が出しているのは**その時点の値だけ**である。

| 出しているもの | 中身 |
|---|---|
| 数字 | `String(Math.max(0, player.lp))` |
| 色 | `--lp-ratio` から `color-mix` で、減るほど赤へ寄せる |
| `banner__lp--low` | 残り4割以下で太字 |
| 立ち絵 | `artStage(player.lp)` でダメージ絵に切り替わる |

**どれも「今いくらか」であって、「いま減った」ではない。**
4000 が 3200 に書き換わるだけで、**減った瞬間を指すものが1つも無い。**

ライフはこのゲームの勝敗そのもの（SPEC 3.7）なので、ここは出すべきである。

#### 9.5.2 出し方は 9.4.2 と同じ

**前回のライフを持ち回り、変わったときだけ一度きりのクラスを足す。**
この画面では `transition` が出ない（9.4.1）ので `animation` を使う。

| クラス | いつ | 動き |
|---|---|---|
| `banner__lp--down` | 前回より減った | 左右に揺れ、赤い光を帯びる（0.4秒） |
| `banner__lp--up` | 前回より増えた | すこし浮き、クリームの光を帯びる（0.4秒） |

**`color` は使わない。** そこは「残り何割か」を出す既存の合図で、奪うと
減り具合が読めなくなる。動かすのは `transform` と `text-shadow` だけにする。

#### 9.5.3 ★ 対戦をやり直したときに誤爆させない

新しい対戦はライフ 4000 から始まるので、**前の対戦の終わり（たとえば 600）から
見ると「増えた」**ことになり、回復の演出が出てしまう。

**ターンが前回より小さくなったら、控えを捨てる。** 新しい対戦は必ずターン1から
始まるので、これで見分けられる。

#### 9.5.4 動きを減らす設定では止める。**代わりは要らない**

伝えているのは「動いた」ことで、**動いた先の値は数字と色として残っている**
（9.5.1 の表）。9.4.4 と同じ理由である。

### 9.6 墓地が増えた瞬間を出す（2026-10-23 の続き）

#### 9.6.1 なぜここか

9.5 でライフを出したので、**残っている「数字が黙って書き換わる場所」は札束の数**である。

| 札束 | 増える／減る | いま出ているもの |
|---|---|---|
| 山（`pile--deck`） | ドローで減る | 数字だけ |
| **墓（`pile--grave`）** | **破壊・解決・手札切りで増える** | **数字だけ** |

**墓が増えたときだけ出す。** 山が減るのはドローで、**引いた札は手札に現れる**ので
別の手がかりがある。墓は「何かが盤から消えた」ことの受け皿で、
**相手の番の早送り中はとくに見落としやすい。**

#### 9.6.2 出し方は 9.4.2 / 9.5.2 と同じ

前回の数を**持ち主と種類ごとに**持ち回り、増えた描き直しだけ
`pile__count--up` を足す（0.4秒）。動かすのは `transform` と `text-shadow`。
やり直しの誤爆は 9.5.3 と同じ歯止め（ターンが戻ったら控えを捨てる）で防ぐ。

**減ったときは出さない。** 墓が減るのは蘇生（`revive`）だけで、
**戻った姫神が盤に現れる**ので別の手がかりがある。

#### 9.6.3 動きを減らす設定では止める。**代わりは要らない**

伝えているのは「増えた」ことで、**増えた先の数は数字として残っている**。
9.4.4 / 9.5.4 と同じ理由である。

### 9.7 引いた札を分かるようにする（2026-10-25）

#### 9.7.1 なぜここか

9.4〜9.6 で「向き」「ライフ」「墓地」を出した。**手札に札が1枚増えることにも、
いま何の手がかりも無い。** 右端に黙って1枚増えるだけである。

姫神演義は同じところに `card--draw` を置いており、**動かさない端末のためには
静止した縁まで足してある**（maniwa-tcg SPEC 9.4.18）。こちらにも同じ扱いを置く。

#### 9.7.2 出し方は 9.4.2 と同じ

**引いた札は手札の末尾に積まれる**（`reduce.ts` の `hand: [...side.hand, top]`）。
**手札の枚数が前回より増えていたら、末尾の札に一度きりのクラスを足す。**

| クラス | 動き |
|---|---|
| `card--drawn` | 下から浮き上がりながら現れる（0.26秒） |

手札に出るのは**自分の札だけ**なので、控えるのは枚数ひとつでよい。
やり直しの誤爆は 9.5.3 と同じ歯止め（ターンが戻ったら控えを捨てる）で防ぐ。

#### 9.7.3 動きを減らす設定では、**静止した縁を置く**

ここは 9.4.4 / 9.5.4 / 9.6.3 と違い、**代わりを置く**。
増えたことを示すものが**数字でも位置でも残らない**（手札の枚数は画面に出ていない）ため、
動きを消すと手がかりが完全に無くなる。姫神演義が 9.4.18 で同じ結論を出している。

`outline` を使う。**`.card--selected`（実線3px・offset 1px）とは太さと間隔で見分ける**
（実線2px・offset 3px）。選ばれている札には縁を足さない（`:not(.card--selected)`）。

> **★ 止めるほうに `:not()` を付けてはいけない（2026-10-25 実測）。**
> 最初 `animation: none` も `:not(.card--selected)` の中に書いたところ、
> **引いた札がそのまま選ばれている描き直しで動きが止まらなかった**
> （計算後の `animation-name` が `cardDrawn` のまま）。
> **止めるのは全部、縁だけ `:not()`** の2本に分ける。

### 9.9 攻撃している姫神と、狙われている姫神が分からない（2026-10-28）

#### 9.9.1 測って分かったこと：**戦闘に演出が1つも無い**

この画面の `@keyframes` は8つで、全部数えるとこうなる。

| 動き | 何に出る |
|---|---|
| `cardFlipToDefense` / `cardFlipToAttack` | 表示形式が変わった（9.4） |
| `lpDown` / `lpUp` | ライフが動いた（9.5） |
| `pileUp` | 墓地が増えた（9.6） |
| `cardDrawn` | 札を引いた（9.7） |
| `openable` | 開ける伏せカード（8.2） |
| `detailIn` | 詳細の幕 |

**攻撃そのものに当たるものが1つも無い。** `view.ts` が姫神に足すクラスも
`card--defense` / `card--facedown` / `card--spent` / `card--selected` だけで、
**「いまこの子が攻撃している」「この子が狙われている」を示すものが無い。**

姫神演義には `card--lunge`（踏み込み）と `card--hit`（被弾）が最初からある。
**こちらには対応するものが無い。** 戦闘はこのゲームの中心なので、ここが空なのは大きい。

#### 9.9.2 とくに困るのは、割り込みの2択が出ている間

9.8.5 で撮った割り込みの画面を見ると、**どの姫神がどの姫神を攻撃しているのかが
画面のどこにも出ていない。** 「攻撃されています。伏せカードを開きますか？」と
聞かれている側は、**何に対して答えるのかが分からないまま**選ぶことになる。

`state.pendingAttack` は `{ attacker, target, negated }` を持っていて、
**チェーンの窓が開いているあいだ残る**（SPEC 11.1）。読む材料はすでにある。

#### 9.9.3 出し方 — 持続する印と、宣言の瞬間の動きを分ける

**2つに分ける。役割が違う。**

| | 何に付く | いつ | 形 |
|---|---|---|---|
| `card--striking` | 攻撃している姫神 | `pendingAttack` があるあいだ**ずっと** | **静止した縁**（実線・暖色） |
| `card--struck` | 狙われている姫神 | 同上 | **静止した縁**（破線・暖色） |
| `card--strike-up` / `card--strike-down` | 攻撃した姫神 | **攻撃が済んだ描き直し1回だけ** | 動き（相手側へ踏み込む） |

**持続する印は静止させる。** 状態から直に決まるクラスに `animation` を付けると
描き直しのたびに再生される（9.4.2 で決めた形の裏返し）。
踏み込みだけは 9.4.2 と同じ「前回を持ち回って一度きり」の形にする。

ダイレクトアタック（`target === null`）では `card--struck` は出ない。狙う札が無いためである。

##### ★ 踏み込みを `pendingAttack` で出してはいけない（2026-10-28 実測）

最初は踏み込みも `pendingAttack` が現れた瞬間で出すつもりで書いた。**出なかった。**

`advanceChain` は、どちらも割り込めないとき**同じ `reduce` の中で**
`resolveAttack` まで進めて `pendingAttack` を消す。つまり
**`pendingAttack` が描き直しに現れるのは、チェーンの窓が開いたときだけ**である。
チェーンの無いふつうの攻撃では、踏み込みが**一度も出なかった**（実測0件）。

踏み込みは `hasAttacked` が **false → true に変わった瞬間**で出す。
これならチェーンの有無に関わらず、どの攻撃でも出る（実測4件）。

**持続する印（`card--striking` / `card--struck`）のほうは `pendingAttack` のままでよい。**
9.9.2 に書いたとおり、**それが要るのはチェーンの窓が開いているあいだだけ**だからである。

#### 9.9.4 踏み込む向きは、どちらの側かで決める

自分の姫神は上へ、相手の姫神は下へ踏み込む。`.field` の並びがそのまま向きになる。
姫神演義の `lungeUp` / `lungeDown` と同じ考え方である（9.4.13）。

#### 9.9.5 動きを減らす設定

**踏み込みは止めるだけでよい。** 攻撃した姫神には `card--spent`（もう攻撃した印）が
そのまま残り、チェーンの窓では `card--striking` / `card--struck` の**静止した縁が残る**。
動きを消しても「誰が攻撃したか」「誰が誰を狙っているか」は画面から消えない。
9.4.4 / 9.5.4 / 9.6.3 と同じ扱いで、9.7.3 のように代わりを置く必要はない。

#### 9.9.6 実測（2026-10-28）

| 印 | 出た回数 | 計算後のスタイル |
|---|---|---|
| `card--strike-down` | **4**（通常） | `strikeDown 0.34s` / 山で `translateY(10px)` |
| `card--strike-down`（reduce） | 4 | `animation: none` / `transform: none` |
| `card--striking` | **1**（割り込みの窓で） | `box-shadow: クリーム 2px ＋ 朱 7px` / `outline` は変えない |
| `card--struck` | **0** | — |

**`card--struck` は、この走りでは一度も出ていない。** 当たった1回の割り込みが
**ダイレクトアタック**（狙う姫神がいない）だったためで、9.9.3 のとおり出ないのが正しい。
規則そのものは、盤の姫神に当てて `box-shadow: 朱 2px ＋ クリーム 7px`（層が逆）に
なることを確かめてある。**出ているところは、まだ見ていない。**

### 9.10 相手が引いた瞬間が、どこにも出ていない（2026-10-29 実測）

#### 9.10.1 9.6.1 で置いた前提は、自分の側にしか当てはまっていなかった

9.6（墓地が増えた瞬間）で「**増えたときだけ出す**」と決めたとき、理由をこう書いた。

> 山が減るのはドローで引いた札が手札に現れ、墓が減るのは蘇生で戻った姫神が盤に現れるので、
> どちらも別の手がかりがある。

**「引いた札が手札に現れる」のは自分の側だけである。** 相手の手札は画面に出ていないので、
**相手がドローしても、山の数字が1つ減るほかに何も起きない。**

12試合を自動で回して数えた実測がこれである。

| 数字 | 回数 | 別の手がかり |
|---|---|---|
| **相手の山が減った** | **89** | **無い**（相手の手札は見えない） |
| 自分の山が減った | 82 | 引いた札が手札に出る（9.7 の `card--drawn`） |
| 自分の墓が増えた | 59 | 9.6 で出している |
| 相手の墓が増えた | 30 | 同上 |
| 墓が減った（両側） | 各5 | 蘇生。戻った姫神が盤に現れる |

> 山が**増えた**（両側で各11回）は、12試合を回すあいだの**仕切り直しの数**である。
> 対戦中に山が増えることは無い。

相手の山の数字には `animation` も `transition` も当たっていない（計算後のスタイルで確認）。

#### 9.10.2 出すのは相手の山だけにする

| 数字 | 出すか | 理由 |
|---|---|---|
| **相手の山が減った** | **出す** | 相手の引いた札はどこにも現れない。数字以外に手がかりが無い |
| 自分の山が減った | 出さない | 引いた札が手札に出る（9.7）。同じ出来事に2つ印を付けない |
| 墓（両側） | 出している | 9.6 のまま |

姫神演義が 9.4.23 で**同じ結論**に達している（あちらも「相手の山札が減った」だけを出した）。

#### 9.10.3 出し方

`pile__count--up` と対にして `pile__count--down` を足す。
`pile()` はすでに持ち主と種類で前回の枚数を持ち回っている（9.6.2）ので、
**条件を1つ足すだけ**で済む。

動かすのは `transform` と `text-shadow` だけ（9.5 / 9.6 と同じ）。
`pileDown` は `pileUp` と**逆向きに沈む**ので、上下で増減を見分けられる。

#### 9.10.4 動きを減らす設定

9.6.3 と同じく**止めるだけでよい**。減った先の数は数字として残る。
**9.4.23 の姫神演義とはここが違う。** あちらは静止した縁を置いたが、
こちらの札束は `山` という文字と数字が常に並んでいて、**数そのものが読める形**になっている。
